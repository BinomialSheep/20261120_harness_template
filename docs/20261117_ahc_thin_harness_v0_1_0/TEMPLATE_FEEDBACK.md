# 雛形へのフィードバック

ahc_thin_harness の雛形作成担当に渡す、問題によらない指摘の一覧。問題固有のことは書かない。新しい指摘は末尾に足す。

## 1. 毎回読み込まれる指示ファイルに雛形作成の経緯を書かない（ユーザー指摘）

- 起きたこと：`AGENTS.md` に、エージェントの行動に関係しない記述が多く入っていた。
  - 「本バージョンにAB-MCTS/Beads/ダッシュボード/自動LLMモデル選択はない。わざと薄く保つ」のような作成経緯
  - 想定する大会区分や、限界の説明
  - CLIが既に強制しているルール
  - `cp config.example.json` から始まる実行例の全文

  AGENTS.md は毎回読み込まれるので、こうした記述はそのままトークンの無駄になる。`docs/SETUP.md` も、オーケストレーターに `docs/DESIGN.md` を読ませる手順になっている。
- 次の雛形で：AGENTS.md には、エージェントの行動を変える指示だけを書く。worker の `task.md` など、毎回読まれる他の指示も同じ。各行について「これが無いとエージェントの行動が変わるか」を確かめ、変わらない行は削るか、人間向けの文書に移す。オーケストレーターが読む文書は AGENTS.md だけで足りるようにする。
- このリポジトリでは：AGENTS.md を行動指示だけに書き直した（6.2KB → 3.5KB）。

## 2. `.gitignore` の `config.json` が `examples/toy/config.json` まで除外する（展開時に判明）

- 起きたこと：パターンがルートに限定されていないので、デモ用の設定がコミットされない。そのため clone した先で `demo` とテストが失敗する。
- 次の雛形で：`/config.json` とルートに限定する。
- このリポジトリでは：`examples/toy/config.json` を強制追加し、`config.json` 自体もGit管理にした。

## 3. `problem/tools/README.md` のプレースホルダが公式ツールのREADMEとぶつかる（展開時に判明）

- 起きたこと：AHCの公式ツールにはたいてい `README.md` が含まれる。そのため配置するとプレースホルダ（アダプタの約束事）が上書きされる。
- 次の雛形で：アダプタの約束事は `docs/SETUP.md` に書き、`problem/tools/` には何も置かない。
- このリポジトリでは：公式のREADMEを残し、アダプタの説明は `problem/tools/LOCAL_JUDGE.md` に書いた。

## 4. 公式ツールのビルド済みバイナリの置き場所が決まっていない（展開時に判明）

- 起きたこと：ラウンドのスナップショットと worker へのコピーでは `target/` が除外される。そのため `cargo build` の成果物をアダプタからそのまま使えず、置き場所とビルド手順を問題ごとに考えることになる。
- 次の雛形で：`problem/tools/bin/`（Git管理外）と、公式ツールをビルドしてそこへ置くスクリプトを雛形に含める。
- このリポジトリでは：`scripts/build_tools.sh` を追加した。

## 5. `claude` engine の既定値では worker が検証できず、隔離も効かない（展開時に判明、実機では未確認）

- 起きたこと：
  - `claude -p --permission-mode acceptEdits` だけでは Bash が許可されないので、worker がコンパイルや `quickcheck.py` を実行できない。
  - workspace を `git init` する隔離は Codex には効くが、`claude` は親ディレクトリの `CLAUDE.md` を読んでしまう。
- 次の雛形で：`--safe-mode`、`--permission-prompts none`、`--allowedTools`（quickcheck とコンパイラ）を付けた例を、実機で確かめてから載せる。
- このリポジトリでは：`config.json` に上記を設定した（まだ実行していない）。

## 6. 評価で現bestと候補の条件が揃っていない（展開時に判明）

- 起きたこと：
  - 現bestは単独で採点し、候補は並列で採点する。そのため時間いっぱい探索する解法では、CPUの取り合いの分だけ候補が不利になる。
  - 候補内のケースは逐次実行なので、1.8秒のソルバーだと1候補あたり約30分かかる。
- 次の雛形で：ケース単位で並列化し、現bestと候補を同じ並列度で混ぜて採点する。
- このリポジトリでは：R0003から対応した。現bestと全候補のケースを1つの待ち行列に交互に入れて並列12で採点し、各 `scores.csv` にはseed順の連続した分だけを書く（再開と早期打ち切りはそのまま）。Aの評価は約1時間から約27分、Bは約1時間から約5分になった。

## 7. Pythonの必要バージョンが実態と合っていない（展開時に判明）

- 起きたこと：READMEは3.11以上を求めるが、3.11固有の機能は使っておらず、3.10でも全テストが通る。要件に合わせて `.venv` を作ったので、コマンドが `python3` から `.venv/bin/python` に変わった。
- 次の雛形で：要件を実態に合わせるか、CLIの起動時にバージョンを確かめる。
- このリポジトリでは：`.venv`（3.12）を使っている。

## 8. `claude -p` の worker に何が渡るかは、実機で確かめないと分からない（開始前の確認で判明）

- 起きたこと：オーケストレーター（VS Code拡張）のセッションには `AGENTS.md` が読み込まれていた。worker の workspace はリポジトリの中にあるので、worker にも渡るおそれがあった。そこで config.json と同じフラグで `claude -p`（CLI 2.1.260）を起動し、読み込まれた指示を答えさせた。
  - デバッグログ（`--debug-file`）には指示ファイルの読み込みが記録されない。そのため判定はモデルの自己申告に頼り、陽性対照（自動メモリの索引 `MEMORY.md` を検出できること）で裏付けた。
  - 読み込まれた指示：

    | 起動場所 | `--safe-mode` なし | `--safe-mode` あり |
    |---|---|---|
    | リポジトリ直下 | 自動メモリの索引 | なし |
    | `git init` していないサブディレクトリ | 自動メモリの索引 | 未確認 |
    | `git init` したサブディレクトリ（worker と同じ形） | なし | なし |

  - `claude -p` は、リポジトリ直下から起動しても `AGENTS.md` を読まなかった。
  - 漏れる経路は自動メモリだった。オーケストレーターはメモリに研究の知見を書くことがあるので、索引が worker に渡ると情報漏れになる。
  - engine の argv に `--model` が無いので、worker のモデルはユーザー設定（`"model": "opus"`）で決まり、`claude-opus-5` で動いた。オーケストレーターは `claude-opus-5-5` だった。
  - `--model claude-opus-5-5` を付けると、worker は起動直後に API の400エラーで失敗した。PATH 上の `claude`（端末のCLI、2.1.260、自動更新オフ）がこのモデルに対応していなかった（2.1.280以上が必要）。オーケストレーターを動かす VS Code 拡張には、別に新しいCLI（2.1.326）が同梱されていた。
  - 2.1.326 でも、worker と同じ形では何も読み込まれなかった。リポジトリ直下から `--safe-mode` なしで起動しても、`AGENTS.md` は読まれなかった。
- 次の雛形で：
  - workspace ごとの `git init` と `--safe-mode` を両方残す。どちらか一方でも自動メモリは渡らなかったが、片方が外れても漏れないようにする。
  - engine の argv に `--model` を明示し、worker のモデルを個人の設定に左右させない。
  - worker が使うCLIのバージョンを、起動前に確かめる手順を入れる（`claude --version`、または短い `claude -p` を1回）。worker の失敗は `job.json` の `worker_failed` と `agent.stdout` でしか分からないので、10並列のAで初めて気づくと影響が大きい。
  - 上の確認手順（陽性対照つき）を、engine を初めて使うときやCLIを替えたときの手順として docs に載せる。
- このリポジトリでは：worker と同じ形では何も読み込まれないことを確かめた。`--model claude-opus-5-5` を付け、`run-workers` は VS Code 拡張に同梱のCLIを PATH の先頭に置いて実行している。

## 9. 利用上限で途中終了した worker が、完走した worker と同じ「提出済み」になる（R0002で判明）

- 起きたこと：サブスクで A（10並列）を始めて約5分で、10体中7体が5時間の利用上限に達して止まった（`agent.stdout` は "You've hit your 5-hour limit" の1行、終了コード1）。直前に B（1体32分）とオーケストレーター自身の作業があった。
  - 止まった worker も、`main.cpp` が途中まで書かれていれば `submitted` として凍結される。違いは `job.json` の `agent_outcome: error` だけで、`run-workers` の結果でも目立たない。
  - `_worker` は `submitted` の job を再実行せず、`submit`・`fail` は `prepared` の間しか使えない。`close` は未評価の提出があると拒否する。そのため、途中の版を評価するか、state ファイルを手で書き換えるしかない。
  - 完走した worker は約5分で終わっていた。A の20分は、多くの案で上限として余っている。
- 次の雛形で：
  - `run-workers` の結果で、途中終了（`agent_outcome` が `ok` 以外）を目立たせる。オーケストレーターがその job を再実行するか失敗扱いにできるコマンドを用意する。
  - 上限のメッセージを検出したら、まだ起動していない worker を起動しない。
  - 利用上限のあるプランでは、A の並列数・時間・モデル・effort を上限から逆算して決める手順を docs に書く。
- このリポジトリでは：R0002 は途中終了の7体も含めてそのまま評価した。

## 10. worker の effort が個人の設定に左右される（R0002のあとにユーザー指摘）

- 起きたこと：engine の argv に `--effort` が無かった。そのため worker の effort は、ユーザー設定（ここでは `~/.claude/settings.json` の `modelSettings` に、`claude-opus-5-5` の `effortLevel: xhigh`）に左右されうる。`--safe-mode` のもとでこの設定が効くかは確かめていない。effort が高いと、worker 1体あたりの消費が増え、9の利用上限に早く達する。
- 次の雛形で：`--model` と同じく `--effort` も engine の argv に明示する。worker の消費は「並列数×時間×effort」で決まるので、利用上限のあるプランで A と B の effort をどう選ぶかを docs に書く。
- このリポジトリでは：R0003 から `--effort high` を明示した。

## 11. `codex` engine の既定値では Web を調べられ、seed の制限も効かない（Codex への切り替えで判明）

- 起きたこと：雛形の argv（`codex exec --sandbox workspace-write --cd {workspace} -`）を、Codex CLI 0.169.1（ChatGPTのPlusプラン）で確かめた。
  - モデルと effort が個人の `~/.codex/config.toml` で決まる（10と同じ問題）。
  - 既定では組み込みの `web_search` が使える。`-c web_search="disabled"` を付けても、ChatGPTの連携アプリ（`codex_apps` のMCPにある `search_service.web_run`）で検索できた。`--ignore-user-config` と、`apps`・`plugins`・`browser_use` などの機能の `--disable` を合わせると、Webの道具は無くなった。サンドボックスのネットワーク遮断は、モデル側の検索ツールには効かない。
  - claude の `--allowedTools` に当たるコマンドの許可リストが無い。workspace には公式ツールがあるので、A の「seed0だけ」は task.md の指示でしか守らせられない。
  - `workspace-write` のサンドボックスが止めるのは書き込みとネットワークだけで、読み取りはディスク全体でできる（過去の `runs/` も読める）。
  - worker に何が渡ったかは、セッション記録（`~/.codex/sessions/**/rollout-*.jsonl`）で確かめられる。渡った指示文（`AGENTS.md` を含む）とツール一覧が残るので、8のようにモデルの自己申告に頼らなくてよい。
  - 利用上限（5時間枠と週間枠）は、`codex app-server` の `account/rateLimits/read` で読める。同じプロトコルにはリセット権を消費するメソッドもあるので、読み取りのメソッドだけを許可リストで送る。
- 次の雛形で：
  - codex の argv 例に、モデル・effort・`--ignore-user-config`・Webに届く機能の無効化・`--json` を入れる。
  - コマンドを制限できない engine には、`--json` のイベント列から許可外の seed、公式ツールの直接実行、workspace 外の参照を洗い出す監査スクリプトを付ける。
  - engine を初めて使うときの確認手順（Webの道具が無いこと、指示ファイルが渡らないこと、サンドボックスの範囲）を、セッション記録とサンドボックスの直接実行で確かめる形で docs に載せる。
  - 利用上限を読む読み取り専用のスクリプトを入れ、ラウンドの前後で確かめる手順にする。
- このリポジトリでは：`config.json` の codex engine に上記のフラグを付け、`scripts/codex_audit.py` と `scripts/codex_limits.py` を追加した。R0006（Bラウンド1体、gpt-6.2-sol・effort high）で動作を確かめた。
  - worker は59分で完走し、有効な候補を提出した。Plusプランの使用率は、5時間枠が19ポイント、週間枠が3ポイント増えた。
  - 監査では、Web・MCP の利用も workspace 外の参照も無かった。ただし quickcheck を通さず `score_case.py` を直接呼んで、seed 0〜9 を採点していた（Bの許可範囲内）。task.md に「採点は quickcheck.py だけで行う」とは書いていなかったので、R0007から1行足した。

## 12. worker の engine として claude と codex を使い分けられるようにする（ユーザー指摘）

- 起きたこと：雛形には `claude` と `codex` の両方の argv 例があるが、どちらも実機では確かめられていなかった（5・11）。このリポジトリは claude だけで始めて、サブスクの利用上限に当たった（9）。そこで codex も使えるように整えた（11）。今後は両方を使い分けたい。
  - engine はラウンド単位でしか選べない（`run-workers --engine`）。A の10体は、すべて同じ engine で動く。
  - どの engine で動かしたかは、`run-workers` の直後の `state.json` にしか書かれない。`evaluate` と `close` でこのファイルが上書きされるので、ラウンドを閉じると記録が消える。`job.json` と `result.json` には engine の欄が無い。
- 次の雛形で：
  - claude と codex を対等に扱う。どちらにも、実機で確かめた argv 例（モデルと effort の固定、Webの無効化、隔離）と、初めて使うときの確認手順を付ける。
  - engine ごとの違いを docs に表でまとめる。項目は、コマンドの許可リストの有無（claude にはあり、codex には無いので監査が要る）、読み込まれる指示ファイルと隔離のしかた、Webの道具を外すフラグ、ログの形式、利用上限の読み方。
  - 候補ごとに、使った engine・モデル・effort を `job.json` と `result.json` に記録する。engine による違いを、結果と結びつけて振り返れるようにする。
  - 1つのラウンドの worker を engine ごとに振り分けられるようにする（例：A の10体を claude と codex に5体ずつ）。利用上限を2つのサブスクに分けられ、片方が上限に達してもラウンドが止まらない。
  - ラウンドの前に、各 engine の利用上限の残りを確かめてから engine と並列数を決めるよう、AGENTS.md に1行入れる。
- このリポジトリでは：codex engine を整え（11）、R0006 から `run-workers --engine codex` で使えるようにした。1つのラウンドで engine を混ぜることと、候補ごとの engine の記録はまだできない。

## 13. codex の worker は、親ディレクトリの AGENTS.md を自分から読みにいく（R0008で判明）

- 起きたこと：codex の A（10体）で、ほぼ全員が最初に `for f in AGENTS.md ../AGENTS.md ../../AGENTS.md ...; do cat "$f"; done` のようなコマンドで、作業場所の上の階層の `AGENTS.md` を探した。2体はリポジトリ直下（5階層上）まで遡っていて、オーケストレーター向けの `AGENTS.md` を読めた。workspace を `git init` しても、自動で読み込まれないだけで、モデルが自分で読みにいくのは止められない（読み取りはサンドボックスで制限されない）。
  - 読まれた `AGENTS.md` には得点や経緯は無く、他のラウンドの成果物（`runs/`、`best/`）を読んだ形跡も無かった。
  - 同じラウンドで3体が、DNS の失敗（`failed to lookup address information`）による再接続の失敗で、20分の上限まで止まった（`agent_outcome: timeout`）。途中の `main.cpp` が提出済みとして凍結された（9と同じ問題）。
- 次の雛形で：
  - worker の作業場所を、オーケストレーターの `AGENTS.md` があるディレクトリの外（例：`/tmp` の下や、リポジトリと兄弟のディレクトリ）に作る。
  - 作業場所の中に、課題を指す短い `AGENTS.md` を置く。codex は作業場所のルートの `AGENTS.md` を自動で読むので、外へ探しにいく動機が減る。task.md にも「作業場所の外のファイルを読まない」と書く。
  - codex の監査で、作業場所の外の読み取りを一覧にして報告する（今の `codex_audit.py` は注意として出すだけ）。
- このリポジトリでは：R0008 はそのまま評価した。R0009 から、`prepare` が各作業場所に短い `AGENTS.md`（課題は `task.md`、外は読まない）を置き、task.md にも外のファイルを読まない1行を足した（`thin/core.py`）。作業場所をリポジトリの外へ移すことは、まだしていない。

## 14. トークンの使用量を記録していない（ユーザー指摘）

- 起きたこと：トークンを節約しようとして、まず測ろうとしたところ、記録がほとんど無かった。
  - `claude` の worker は `claude -p` のテキスト出力で、`--no-session-persistence` も付けているので、トークンの記録がどこにも残らない。
  - `codex` の worker は `--json` の `turn.completed` に合計が出るが、時間の上限で止められると出る前に終わるので、何も残らない（R0008・R0009 で20体中7体）。`--ephemeral` なのでセッション記録も無い。
  - オーケストレーターのセッション記録（`~/.claude/projects/`）には残るが、1つの応答が content block ごとに別の行になり、同じ usage が繰り返される。そのまま足すと数倍に数えてしまう。
  - ラウンドとの対応が無いので、どのラウンドでどれだけ使ったかが分からない。`~/.claude` の記録は既定で30日で消える。
  - 集計してみると、オーケストレーターを1つのセッションで続けたため、1回の呼び出しで読む文脈が R0001 の22万から R0011 の53万へ増え続けていた。また、1時間を超えて待ったあとは、キャッシュの期限切れで文脈全体を書き直していた。
- 次の雛形で：
  - worker の engine の argv で、トークンが呼び出しごとに残る出力形式を使う。`claude -p` は `--output-format stream-json --verbose` で、呼び出しごとの usage と、利用上限の使用率（`rate_limit_event`）が出る。codex は `--ephemeral` を外し、worker のセッション記録を job のディレクトリへ移す。ただし Codex の SQLite には痕跡が残るので、隔離の方針とあわせて決める。
  - worker の終了時に、engine・モデル・effort とトークンの要約を `job.json` に書く。close のときに、ラウンドの消費を `usage.json` に書く。
  - 対話セッションの消費を時刻だけでラウンドに割り当てない。リポジトリではラウンド以外の作業（ドキュメント整備、計測、別セッションでの相談）も並行して行うので、混ざる。そのラウンドのコマンドを実行したセッションとターンで割り当て、それ以外は「ラウンド外」として別に数える。
  - サブスクで使うときの主指標は、ラウンドごとの利用上限（5時間枠・週間枠）の使用率の増分にする。トークン数は、キャッシュなし入力・キャッシュ書き込み・キャッシュ読み出し・出力に分けて見る（重みが大きく違う）。
  - オーケストレーターはラウンドごとに新しいセッションで始められるよう、状態をファイルに置き、AGENTS.md の手順を「status から再開する」形に保つ。
  - ハーネスの状態（best・runs）はファイルにあるが、オーケストレーターの判断（何が効いたか、次の狙い）はユーザーへの報告の中にしか無い。`runs/` を全部読み直すと文脈が大きくなる。研究の記録の雛形を置き、close の前に更新する手順にする。
- このリポジトリでは：`thin/usage.py` と `scripts/token_report.py` を足し、上の記録を R0012 から残すようにした。R0001〜R0011 の集計は `docs/レポート/トークン計測レポート.html` にまとめた。R0012 から `docs/RESEARCH_LOG.md` を置き、AGENTS.md の手順1で読み、手順6で close の前に更新するようにした。

## 15. codex の worker が、実行中のコマンドを短い間隔で見に行く（R0012で判明）

- 起きたこと：codex の worker は、コマンドの待ち時間（`exec_command` の `yield_time_ms`）を毎回 1000ms か 100ms に指定していた（既定は10秒、上限は30秒）。quickcheck はコンパイルと実行で10秒前後かかるので、ほぼ毎回途中で戻り、結果を取りに行くだけの呼び出し（`write_stdin`）を重ねた。A の10体で272回のうち61回がこれで、1回ごとに文脈全体を読み直すため、5時間枠の消費の約22%になった。ただし無くして減るのは、文脈を読み直した約5%だけで、受け取る結果と思考は次の呼び出しに移る（R0014 までの記録で推定した重みによる。Codex の使用率は出力でほぼ決まり、キャッシュ読み出しの重みは入力の約0.04倍）。残り時間を知るためだけに時刻を見る呼び出しも8回あった（約3%）。
- 次の雛形で：
  - task.md に、時間のかかるコマンドは終わるまで1回で待つことを書く（codex なら `yield_time_ms` を 30000 にする）。
  - quickcheck の出力に、実行時間と worker の残り時間を入れる。締め切りは worker を起動するときに作業場所の設定に書く。
  - worker の記録から、待つだけの呼び出しと時刻を見る呼び出しの回数を数え、ラウンドごとに見られるようにする。
- このリポジトリでは：R0013 から、上の3つを入れた（`thin/core.py`、`scripts/quickcheck.py`、`thin/usage.py`）。R0013 では、worker が全コマンドで待ち時間を30秒に指定し、待つだけの呼び出しと時刻だけの呼び出しは0回になった。A の1ラウンドの5時間枠の増分は45から42ポイントになった（案が違うので目安）。

## 16. B でパラメータ調整ができない（ユーザー指摘、R0014）

- 起きたこと：B の worker を「判断を変えない高速化」にしようとしたところ、ユーザーから、定数をハイパーパラメータにして Optuna で調整すること、より推論の強い設定で、2時間ではなく8時間かけることを求められた。雛形の B は「許可された debug seed（最大20）を1件ずつ quickcheck する」だけで、task.md も「大量のシード生成、並列ベンチ、長時間学習はしない」と禁じていた。調整に要る、多数のケースをまとめて採点する手段も無かった。
- 次の雛形で：
  - B の設定に、評価のseedと重ならない調整用seedの範囲と同時実行数を置けるようにする。`prepare` は、そのラウンドの評価のseedと重なれば止める。範囲は、将来のラウンドの評価のseed（`first_seed` から1ラウンド1000ずつ増える）とも重ならない遠い所に置く。
  - 1回のコンパイルで多数のseedをまとめて採点するスクリプトを作業場所に置く。許可外のseedは拒否し、同時実行数は評価と同じにする（実行時間で判断が変わるソルバーは、混み具合で結果が変わる）。ソルバーへの環境変数を渡せるようにし、調整用のビルドが環境変数からパラメータを読めるようにする。
  - task.md に、調整用seedを探索と確認の組に分けること、提出するソースを環境変数に依存させないこと、長い待ちの仕方（codex は空の `write_stdin` で最大5分待てる）、終える前に起動したプロセスを止めることを書く。
  - 推論の強さを変えた engine を別名で置き、A の engine はそのままにする。
  - worker の時間切れでは worker のプロセスグループを止めるが、worker が切り離して起動した調整のプロセスは残りうる。評価の前に、残ったプロセスが無いことを確かめる（残ると評価が TLE になる）。
- このリポジトリでは：R0014 から入れた（`config.json` の `workers.tuning_B`・`minutes_B`・`engines.codex_deep`、`thin/core.py`、`scripts/batchcheck.py`、`tests/test_thin.py` の `TuningB`）。調整用seedは 1000000〜1019999、同時実行は12。
- R0014 の結果：worker は8時間の上限に対して49分で終えた。Optuna は30試行（各240ケース）だけで、1試行の標準誤差（約0.09）が、探したい差（0.05前後）より大きかった。task.md の共通の1行「時間を使い切る必要はない」に従ったとみる。調整を課す B では、この1行を外し、試行の数か、1試行に使うケース数の目安を課題に書く。
