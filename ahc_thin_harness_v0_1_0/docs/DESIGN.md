# 設計判断：速さ・試行数・独立性を優先

## 行動A — 10個の並列改善

- オーケストレーターが**本質的に異なる**10案を作る。`new`（親なし）、`continue`（親コード1本）、`combine`（過去の2コードの組合せ）。過去の前例や計測結果はオーケストレーターだけが読む。
- 10個の独立workspaceを作り、各workspaceへ問題文・**公式ツールのコピー**・自分の案・選択済み親ソース・`quickcheck.py`だけを配置。研究ログ、過去スコア、他workerの成果物は入れない。
- 設定したCLIで10workerを並列起動し、各20分で終了する。workerは**seed0だけ**を`python3 quickcheck.py --seed 0`で試す。大規模なseed生成／学習をさせない。
- 最後に10本の`main.cpp`を凍結して独立採点。重複したコードはSHA-256で判定し、評価を再利用する。無効候補はベストにならない。

## 行動B — 1個の深い改善

- 現在のベストだけを親に選ぶ。worker1体、**120分上限**。公式ツールを使い、必要なら許可された少数のdebug seed（初期値0〜9）で確認可能。
- 大規模1000ケース評価はworkerではなく、終了後にオーケストレーターが実施する。Aと同じ品質判定で選別。

## 各ラウンドの評価

- ラウンド番号 `r>=1` では、`first_seed+(r-1)*count` から`count=1000`件を固定。**10候補と現ベストは必ず同じseed集合で比較**する。
- 新ラウンドでは原則新seedに移る。workerには評価seed範囲を渡さず、quickcheckはAでseed0だけを許可する。
- 公式工具は問題ごとに異なるため、`judge.command`の1ケースadapterが`{binary},{seed},{result}`を受け取り、`{"status":"ok","valid":true,"score":<finite number>}`を作る。
- `maximize/minimize`、`paired_difference/paired_log_ratio`が指定可能。差は「改善ほど正」へ揃える。無効／TLE／judge故障はスコア0として入れない。全1000件合法な候補だけが採用可能。
- 10候補の最高値は**勝者選択バイアス**を持つ。1000seedで採用しても本番保証や独立holdoutでの確認ではない。新ラウンドでは新seedで再び現ベストを比較する。
- `promotion_margin`より厳密に改善していない候補は、既存bestの代替へ昇格できない。昇格は**明示した`promote`コマンド**が必要。観測事実と人間／オーケストレーターの判断を区別する。

## A/Bの選択（学習済み自動方策ではない）

各ラウンドの開始時にオーケストレーターが、自分の知識と残時間・計算負荷から選ぶ。

**Aを選びやすい状況**：新規系統を増やしたい、直近の試行が同じ改変ばかり、組合せを広く試したい、10×1000ケース評価の費用が許容できる。

**Bを選びやすい状況**：主力系統の理解が進んでいる、改変が複雑・相互依存、深い設計や正確な差分更新が必要、評価が高価で候補を増やしすぎたくない。

毎回同じ手法だけを試す・機械的に交互にする・人間の思いつきだけで10案を埋める、という運用は推奨しない。高度なAB-MCTSは**この段階では入れない**。この薄い方策の実績が取れてから必要なら追加する。

## 中断とリソース

- 公式ツールは`runs/R####/judge_tools`へラウンド時にコピー・固定。workerが自分のコピーを編集しても採点には影響させない。
- worker並列数A=10、採点並列数は通常1〜2。worker環境ではOpenMP等のスレッド数を1へ抑える。ただしCLIが起動する任意の子孫プロセスへ厳密なCPU/GPU上限を掛ける仕組みではない。
- `round`は失敗時に最初からやり直さず、`status`で対象ラウンドを確認する。1000seed採点はケース単位でCSVへ追記し、同じコンパイル済みartifact・同じtool snapshotなら再開する。
- `best/main.cpp`だけが現在の最良提出候補。変更前ベストは`best/history`へ保存。`runs`・`best`はGit管理外なので、意図的にバックアップを取る。
