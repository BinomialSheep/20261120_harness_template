## 1. タスクの理解

- `ahc_thin_harness_v0_1_0` は変更せず、`ahc_thin_harness_v0_2_0/` を新しく作る。
- 実験（atcoder13live、R0001〜R0019）で見つかった不満を直す。材料は `TEMPLATE_FEEDBACK.md` の16項目、`メモ.md`、研究の記録、実験リポジトリで改造済みのコード。
- 使われ方は、プロジェクトのフォルダに問題文・公式ツール・雛形を置き、「テンプレートに従って環境構築してください」とエージェントに頼む形。人間が手順書どおりに操作するわけではない。
- 「薄く並列させる方式が、ヒューリスティック問題と相性がよい」という評価なので、薄さは残す。
- 優先はトークンの計測と節約。次が、人間の理解と発想を助ける仕組み。

## 3. 方針

1. **薄さを残す。** `prepare → run → evaluate → promote → close` は変えない。足すのは、不具合と運用停止の解消、それに LLM を使わない補助コマンドだけ。補助は `tools/` に分け、使わなくても回るようにする。目安として、`thin/` は1,500行まで、`AGENTS.md` は3.5KBまで。
2. **トークンは、考えることと書くことにだけ使う。** 待つ・測る・調整する・集計する・図を作るのは CLI が行う。
3. **途中で切れても捨てない、巻き込まない。** 利用上限・通信断・環境の故障を、候補の失敗と区別する。
4. **実機で確かめた設定だけを既定にする。** 確かめていないものは「未確認」と書く。
5. **配備の手間を減らす。** 1回だけ読む手順と、毎回読む指示を分ける。

## 4. 変更の中身

優先度は、必＝v0.2.0 に必ず入れる、推＝入れたい、任＝余力があれば。

### 4.1 トークン

| 優先 | 変更 |
|---|---|
| 必 | `usage.py` を移植し、`wait` の数え漏れを直す。engine・モデル・effort を `job.json` と `result.json` に残す |
| 必 | 案数を可変（1〜10）にする。案ごとに engine と effort を指定できる。同じ案を effort 違いで並べる比較もできる |
| 必 | `limits`：利用枠の残りと、前回までの1体あたりの消費から見積もった必要量を出す。足りなければ `run` の前に警告する |
| 必 | 案の JSON に共通文（`common`）を置く。R0015 では約870〜1,230字の案が10個あり、親の説明が毎回重複していた |
| 必 | CLI の出力を短い表にする（全文は `--json`） |
| 必 | worker の `notes.md` に「変更点・構成・確かめられなかった点」を書かせ、昇格時に `best/notes.md` へ写す。オーケストレーターが 80〜170KB の best を読み直さずに済む |
| 必 | `run` と `evaluate` を1回で行う `go`。1時間を超える待ちの前に報告して終え、次は新しいセッションで `status` から続ける手順にする |
| 推 | 親ソースの関数一覧と、親どうしの差分を、worker の作業場所に自動で置く |
| 推 | claude worker の固定分（1回約3万トークン）を `--tools` などで減らす。実機で測ってから既定にする |

### 4.2 評価

| 優先 | 変更 |
|---|---|
| 必 | ケース単位の並列と、現best・候補の混合（実験リポジトリから移植） |
| 必 | 段階式の足切り。各段階で、現best か首位より z×標準誤差を超えて悪い候補を落とす。上位3は残す |
| 必 | 確認評価。首位を未使用の seed で現best と比べ直し、その値で採否を決める。差が十分大きければ省く |
| 必 | TLE は、混んでいないときに単独で最大2回まで走らせ直す（AtCoder の扱いに合わせる）。環境エラーは候補の失敗にせず、評価を中断する |
| 必 | `evaluate --restart`：評価を退避して最初から採点し直す（R0013 で必要になった） |
| 必 | 評価前の検査：負荷、残ったプロセス、空き容量 |
| 必 | アダプタの時間計測を、見回り（`Popen.wait(timeout)`、最大50ミリ秒の丸め）からブロックする待ち方へ変える |
| 推 | アダプタがケースの特徴量（例：壁の数）を返せば、帯ごとの効果を出す |
| 推 | `case`：1ケースを走らせ、入出力と公式ビジュアライザの出力を残す |

### 4.3 worker の実行と隔離

| 優先 | 変更 |
|---|---|
| 必 | 作業場所をリポジトリの外（兄弟ディレクトリ）に作り、短い `AGENTS.md` を置く。上の階層に指示ファイルがあれば doctor が警告する |
| 必 | claude と codex を対等に扱う。モデル・effort・Web の無効化を argv に固定し、CLI の場所（VS Code 同梱版を含む）と最低バージョンを確かめる |
| 必 | 1ラウンドの中で engine を混ぜる（案ごと、または `--mix codex:4,claude:2`） |
| 必 | 途中終了を `interrupted` として区別し、`accept`・`rerun`・`fail` で処理する。利用上限を検出したら、残りの worker を起動しない |
| 必 | 通信断（`Reconnecting... 5/5`）を検出して理由に残す。R0008・R0009 の時間切れ7体のうち5体がこれ |
| 必 | worker の終了時に、作業場所で動いている残りのプロセスを止める（切り離されたものも、作業ディレクトリで見つける） |
| 必 | codex の監査（Web・許可外 seed・作業場所外の読み取り）と、利用上限の読み取りを移植 |
| 推 | task.md を外部テンプレートにし、行動を変えない行を削る |

### 4.4 実験と調整

| 優先 | 変更 |
|---|---|
| 必 | 行動 C（測定・診断）。成果物は `report.md` とデータで、候補が無くても閉じられる。R0016・E01 のような作業を、ラウンドとして記録する |
| 必 | B と C に、複数の親と参考ファイル（`ref/`）を正式に渡せる。R0017 では手で置いていた |
| 必 | `batchcheck` に親との対比較を入れる（平均差・標準誤差・帯別）。R0017・R0018 の worker は自作していた |
| 推 | `probe`：時間を0.5〜8倍にしたときと、同じ版を k 回走らせた最良を、LLM なしで測る（「時間10倍したら」の実験）。時間は時計を遅く見せて伸ばすので、ソースの取り決めは要らない（例で確認済み） |
| 推 | `tune`：Optuna での調整、上位の再評価、未使用 seed での比較、定数の書き戻しを LLM なしで行う |
| 推 | `tune` のための取り決め：`-DLOCAL` ビルドのときだけ、パラメータを環境変数で変えられる |

### 4.5 人間の理解と発想

| 優先 | 変更 |
|---|---|
| 推 | `report`：静的な HTML 1枚を LLM なしで作る。例は `work/report_example/report.html`（入れるか、どの節を残すかはユーザーが判断） |
| 推 | `human/INBOX.md`：思いつきを書く場所。ラウンドの最初に読み、採用した案には出どころを付けて、結果を返す |
| 推 | ラウンド報告に「人間への問い」を1つ入れる |
| 推 | `human/private/`：AI に読ませないメモ。読み取り禁止の設定と AGENTS.md の1行で守る。ファイルの中に書いた禁止は、開くまで分からない |
| 任 | 解法スナップショットを作る定型プロンプト（必要なときに別セッションで使う） |

| 優先 | 変更 |

## 6. 進め方

各段階の終わりで、テストが通り、トイ問題が一周する状態を保つ。

1. **土台**：v0.1.0 を写し、実験リポジトリの改良（並列評価・usage・batchcheck・codex の道具）を移す。`wait` の数え漏れもここで直す。1行に詰めた書き方をほどき、テストを移植する。
2. **トークンと worker 実行**：4.1、4.3。
3. **評価**：4.2。
4. **実験と調整**：4.4。
5. **配備と文書**：4.6。
6. **人間向け**：4.5。
7. **検証と仕上げ**：下の表を終え、CHANGELOG・制限事項を書く。

検証：

| 番号 | 内容 | LLM |
|---|---|---|
| V1 | 単体テストと、疑似 engine による再現（上限到達・時間切れ・切り離しプロセス・通信断） | 使わない |
| V2 | 過去データの再現：段階評価が勝者を落とさないこと。集計が既存のレポートと合うこと | 使わない |
| V3 | `work/` に配備して atcoder13live をつなぎ、R0012 の10候補を再評価し、結果と時間を比べる | 使わない |
| V4 | claude・codex を各1体、トイ問題で動かす。隔離、Web の無効化、記録、claude の固定分の測定 | 使う（要許可） |
| V5 | 配備の通し：空フォルダと SETUP.md だけで配備できるか。トークンを前回の実績と比べる | 使う（要許可・任意） |

## 7. やらないこと

- 非同期の worker、AB-MCTS、常駐プロセス、自動モデル選択、自動提出、機械学習の学習管理。
- マシンの設定変更。
- 過去のフォルダ（v0.1.0、重い雛形、docs、汎用ファイル）の変更。

## 8. 判断してほしいこと

1. V4 の実機確認で、claude と codex のサブスク枠を少し使ってよいか。
2. 人間向けの仕組み（4.5）：レポートの例を見て、入れるか、どの節を残すか。INBOX と問いも合わせて決める。

既定で進めること（違えば変える）：A の既定6案、段階評価 100/300/1000 と確認評価、行動 C の追加、`best/` と各ラウンドの要点の Git 管理。
