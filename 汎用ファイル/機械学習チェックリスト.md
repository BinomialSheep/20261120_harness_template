# CodinGame：機械学習・深層学習・自己対戦・AlphaZero 系チェックリスト

> **目的**：CodinGame Bot Programming で、機械学習・深層学習・強化学習を「対戦で強くなる道具」として使うための実践チェックリスト。Kaggle の検証設計、ゲーム AI の自己対戦、AlphaZero / MuZero / CFR などの知見を横断する。
>
> **対象**：C++ で提出するゲーム AI。学習はローカルの Python / PyTorch 等で行い、提出時は軽量な推論器を組み込む構成も想定する。
>
> **立場**：ここにある手法は採用すべき順番ではなく、状況別の選択肢。**精度・学習効率・勝率・推論コストを別々に測り、最終的には対戦成績で判断する。**
>
> **記号**：`[P0]` ほぼ必須・最初に点検 / `[P1]` 効果が大きく検討優先 / `[条件]` 問題に適合する場合 / `[発展]` 高度または高コスト。
>
> **関連資料**：通常の探索、SA、ビームサーチ、差分評価、データ構造などは [AHC / CodinGame ヒューリスティック探索 Tips](./ahc_codingame_heuristic_tips_checklist.md) を参照。本ファイルは主に「学習する部分」を扱う。
>
> 最終更新：2026-10-29。研究・実装の参考文献は末尾に掲載。

## 0. まず確認する15項目

- [ ] [P0] **学習したい対象**を明示したか（局面価値 `V(s)`、行動価値 `Q(s,a)`、方策 `π(a|s)`、対戦相手モデル、状態遷移、候補生成、ドラフトなど）。
- [ ] [P0] **本当の目的関数**は何か。勝率、順位、得点、リーグ昇格、特定の相手への勝率のどれを最大化するか。
- [ ] [P0] 完全情報／不完全情報、確定／確率的、交互手番／同一ターン複数アクション／同時行動、零和／非零和を分類したか。
- [ ] [P0] **正しいローカルシミュレータ**があるか。既知のルールを学習する前に実装・高速化できないか。
- [ ] [P0] 学習なしで強い**固定ベースライン**（貪欲、探索、手作り評価）を作り、再現可能な対戦評価を用意したか。
- [ ] [P0] 本番で**観測できない情報が入力特徴に混入**していないか（敵の手札・山札、将来の乱数、内部状態など）。
- [ ] [P0] **試合単位**、初期設定、相手、生成時期などのグループを意識して train / validation / test を分けたか。
- [ ] [P0] 1手ごとの予測精度だけでなく、**実際の対戦勝率と実行時間**を測定しているか。
- [ ] [P0] 勝率比較は先後・陣営・初期シード・相手プールを揃え、ばらつきと信頼区間を見ているか。
- [ ] [P0] 価値の**視点（どちらのプレイヤーから見た値か）**、報酬の符号、終端、同一プレイヤー連続手番の扱いを検証したか。
- [ ] [P1] ニューラルネットを大きくする前に、**表現・教師の質・学習ターゲット・探索との接続**を改善したか。
- [ ] [P1] 自己対戦の相手が最新の自分だけになっておらず、過去モデル／異なる戦型／強いベースラインにも勝てるか。
- [ ] [P1] 学習器をボットに入れた結果、**同じ制限時間で探索が何回減るか**まで計測したか。
- [ ] [P1] 改善要素を1つずつ外す**アブレーション**を行い、偶然の上振れを排除したか。
- [ ] [P1] 最終提出と同じ C++ ビルド・入力・モデル・時間制限で動作検証したか。

## 1. 問題分類と手法の選択

### 1.1 ゲームの構造

- [ ] [P0] 観測 `o_t`、内部状態 `s_t`、合法手集合 `A(o_t)`、手番プレイヤー、確率イベント、終局条件を区別したか。
- [ ] [P0] **局面を完全復元できるか**。できないなら `V(s)` より `V(o, history)` / belief を考える必要がある。
- [ ] [P0] 1回の出力が「1アクション」か「同一ターン内のアクション列」かを確認したか。複数行動ならマクロアクション・段階的方策も候補。
- [ ] [P0] 勝敗がゼロ和でも、**採点方式が得点差・順位・平均スコア**なら、その指標と学習目標が一致しているか。
- [ ] [P1] 対戦の長さ、分岐数、合流の多さ、隠れ情報量、ランダム性、ルールシミュレーションの速度を概算したか。
- [ ] [P1] 相手の応答で価値が大きく変わる**戦術局面**と、長期的な位置取りが効く**戦略局面**を分けたか。
- [ ] [条件] 先手後手の非対称性、ドラフトと戦闘の異質性、フェーズごとの観測・行動空間を明示したか。

### 1.2 最初に比較する候補（手法は目的から選ぶ）

| 状況・欲しいもの | まず試す手法 | 次の候補／注意 |
|---|---|---|
| 強い既存ボットがある | 模倣学習（BC）、価値回帰、残差学習 | DAgger、探索による教師改善、RL |
| 局面の良し悪しを数値化したい | LightGBM / 小型 MLP の `V(s)` | TD(λ)、アンサンブル、分布価値 |
| 合法手を高速に並べ替えたい | `Q(s,a)`、pairwise ranking、policy head | 行動マスク、候補生成、多段選択 |
| ルール既知・完全情報・正確に探索できる | αβ / MCTS + 学習評価 | AlphaZero 型の policy+value+search |
| 探索回数が極めて少ない | 高速な value / policy、軽い候補選別 | Gumbel AlphaZero、探索予算配分 |
| 規則が確率的／部分観測 | サンプリング、belief、履歴入力 | IS-MCTS / CFR / ReBeL 等（適用条件を確認） |
| 自己対戦の戦型が偏る | 過去モデルと多様な相手のプール | PFSP、league、PSRO |
| シミュレータが作れない／極めて高価 | オフラインログ学習、モデル学習 | MuZero 系。ただし実装難度・計算費が大きい |
| 学習済みモデルの推論が遅い | 線形・GBDT・小型 MLP、蒸留 | NNUE 的差分更新、量子化、バッチ化 |

**選択の原則**：ゲームのルールが既知で正確なシミュレータを実装できるなら、まずそれを使った探索＋学習評価を比較する。MuZero や大規模 end-to-end RL が常に上位互換というわけではない。

### 1.3 何を学習しないか

- [ ] [P0] 厳密に計算できる特徴・ルール・合法性は**学習で代替する必要があるか**。
- [ ] [P1] 学習器を使う箇所を**評価・候補生成・枝刈り・相手モデル**のどこかに限定できないか。
- [ ] [P1] 特徴量設計や人手の評価関数のパラメータ最適化だけで改善できないか。
- [ ] [条件] 探索の結果を**学習器へ蒸留**し、提出では教師探索を使わない形にできないか。

## 2. 学習基盤・シミュレータ・基準ボット

### 2.1 シミュレータの正しさ

- [ ] [P0] ローカルエンジンと本番リファレンスで、合法手・遷移・得点・終了判定を照合したか。
- [ ] [P0] ランダムイベントと意思決定を分け、**シードを固定して再現**できるか。
- [ ] [P0] すべての行動が合法かをテストし、例外や誤出力の原因をログから追跡できるか。
- [ ] [P0] 対戦で自分が見る観測と、シミュレータ内部の完全状態を**別型・別インターフェース**にしたか。
- [ ] [P0] `terminal`（真の終局）と `truncated`（手数／時間で打ち切り）を区別したか。ブートストラップの可否が変わる。
- [ ] [P1] 遷移・合法手列挙・状態コピー・ハッシュの速度を測定したか。学習速度の律速になりやすい。
- [ ] [P1] 小さい状態で全列挙や全探索と比較し、探索器・価値逆伝播の correctness を確認したか。
- [ ] [P1] 不変条件（資源総量・デッキ枚数・手番など）の property-based / fuzz test を書いたか。
- [ ] [条件] シミュレータの近似が許される場合、どの誤差が行動選択に効くかを測ったか。

### 2.2 学習前のベースライン

- [ ] [P0] ランダム合法手・貪欲・簡易探索・現行最強ボットとの対戦を保存したか。
- [ ] [P0] 同一の対戦条件で「学習なし探索」「学習評価のみ」「学習＋探索」を比較できるか。
- [ ] [P1] 教師ボットの行動・探索スコア・訪問回数・敗因をログに残せるか。
- [ ] [P1] 強い手作り特徴を捨てず、特徴入力や残差ターゲットとして活用できないか。
- [ ] [条件] 特定のフェーズだけ学習に置き換える構成で効果を分離できないか。

### 2.3 工程・実験の独立

- [ ] [P0] `environment` / `selfplay` / `dataset` / `train` / `arena` / `export` / `submission` を独立実行できるか。
- [ ] [P0] 学習モデルと特徴量定義に**バージョン番号**があり、古いデータを誤解釈しないか。
- [ ] [P1] 学習中のデータ生成・評価対戦・最終採点を別の乱数系列にしたか。
- [ ] [P1] 1件の試合ログから対局、推論値、合法手、選択手、結果を再生できるか。

## 3. データ生成・品質・Kaggle 的な検証設計

### 3.1 データの出自と分布

- [ ] [P0] どの**方策・バージョン・対戦相手・シード**が生成したデータか保存したか。
- [ ] [P0] 観測データと `action, reward, next_observation, terminal` の対応が1ステップずれていないか。
- [ ] [P0] **勝った試合だけで学習**していないか。負け・引き分け・劣勢・不利な行動も必要に応じて残す。
- [ ] [P1] 序中終盤、先後、手札・カード種類、局面難度、対戦相手の強さを層別集計したか。
- [ ] [P1] 同じ初期局面／同じ型の相手／自分と同じ戦型にデータが偏っていないか。
- [ ] [P1] **強い方策による局面は狭い**。弱い相手・ノイズ付き方策・探索ノイズ・古いモデルから広い分布を得られないか。
- [ ] [条件] 重要な敗北局面・レアな合法手・戦術分岐を優先収集する。ただし学習時にサンプリングバイアスを意識する。
- [ ] [条件] プレイログ由来の教師は、教師自身の誤判断・戦型の癖・選択バイアスを引き継ぐと理解しているか。

### 3.2 **リーク・評価分割**（Kaggle の重要教訓）

- [ ] [P0] **同一試合の別時点を train/test にまたがらせていないか**。局面単位のランダム分割は高相関・実質重複で過大評価しやすい。
- [ ] [P0] 初期シードやマップ、対戦相手、デッキ／カードプールの類似性が、評価の独立性を損なわないか。
- [ ] [P0] **本番で知り得ない隠し情報・未来の結果を入力**していないか。教師ラベルとして将来結果を使うことと、入力に使うことは違う。
- [ ] [P0] 正規化・標準化・エンコーダ・特徴選択の `fit` は**訓練分割だけ**で実行したか。
- [ ] [P0] 何度も試行錯誤した validation を最終 test と呼んでいないか。未使用の独立 test と相手プールを確保したか。
- [ ] [P1] `GroupKFold` 的に**対局単位・初期設定単位**で分割し、一般化先（未知相手／未知乱数）と一致させたか。
- [ ] [P1] 学習世代が進む時系列データでは、未来世代を学習に使わないテストや、世代外ホールドアウトを検討したか。
- [ ] [P1] **同じルール・同じ自己対戦プール内だけ**で良好な validation が出ていないか。分布外の敵・構成を試す。
- [ ] [条件] ターゲットエンコーディング、相手の強さ推定、統計特徴の構築が test 由来ラベルを使っていないか。
- [ ] [条件] 重複局面はハッシュで識別し、分割間の近重複率も計測できるか。

### 3.3 教師の品質とサンプリング

- [ ] [P0] `z`（最終勝敗・得点）と `q`（探索評価・TD 推定）を**異なるラベル**として扱っているか。
- [ ] [P1] 教師ボットの **探索深さ・訪問数・時間・相手分布**を記録し、教師の信頼度を把握できるか。
- [ ] [P1] 1局面ごとに重みを置くか、1試合ごとに重みを置くかを決めたか。長い試合が学習を支配しないか。
- [ ] [P1] **ほぼ同じ局面の大量反復**でデータ数だけ膨らんでいないか。重複除去・重み・リザーバを検討したか。
- [ ] [条件] リプレイバッファは新旧混合比・最大保持世代・優先度をチューニングしたか。
- [ ] [条件] 優先度付きサンプル（高 TD 誤差、僅差、終盤、レア戦型）は有効か。必要なら重み補正を入れる。
- [ ] [条件] 自己対戦軌跡だけでなく、**探索が捨てた手の価値**を追加教師として活用できないか。

### 3.4 データ生成効率

- [ ] [P0] 学習用に何試合／秒・何手／秒生成できるか測ったか。GPU の前に環境の CPU が律速かもしれない。
- [ ] [P1] 独立試合の並列化・プロセス数・乱数シードの衝突を検証したか。
- [ ] [P1] ログ形式はコンパクトか。バイナリ記録・圧縮・バッチ書き込みのコストを測ったか。
- [ ] [P1] **GPU バッチ推論**のために、複数 self-play ワーカーから問い合わせを集約できるか。
- [ ] [条件] 重い探索ラベルを全局面で作らず、**重要局面だけ深く探索**できないか。
- [ ] [条件] 学習済み value で大半の局面を評価し、一部だけ探索で再評価する **reanalysis** を検討したか。

## 4. 特徴量・入力表現（高次元でも学習可能にする）

### 4.1 何を入力するか

- [ ] [P0] 意思決定に必要な**公開情報・自分の私的情報・過去の観測**を取りこぼしていないか。
- [ ] [P0] 特徴量の意味・単位・範囲・欠損値・対称性を仕様化したか。
- [ ] [P1] 手作り評価で役立った情報（距離、連結性、自由度、資源、危険度、テンポ、将来行動可能性）を残せないか。
- [ ] [P1] 絶対値と相対値を使い分けたか（HP と HP 差、資源と相手との差、残りターンなど）。
- [ ] [P1] **次の手で変わる特徴**と、ほぼ不変な大域特徴を分けたか。差分推論に使える。
- [ ] [P1] フェーズ、手番、先後、自分／相手の視点、ゲームの残り時間を明示したか。
- [ ] [条件] 直近行動履歴や相手の公開された選択履歴が戦略に必要なら、履歴特徴か RNN を検討したか。
- [ ] [条件] 盤面の対称変換、プレイヤー入れ替え、カードの順序置換が**本当に意味を保存**するか検証したか。

### 4.2 情報を過剰に潰さず学習させる

- [ ] [P1] 「特徴量が多いから」だけで細かな情報を捨てず、**パラメータ共有・正則化・階層構造**で対処できないか。
- [ ] [P1] カテゴリ ID を大きな数値として入れていないか。**one-hot / embedding** にしたか。
- [ ] [P1] エンティティ（カード、ユニット、セル等）は**共通エンコーダ＋集約**を使い、同じ意味の特徴を学習共有できないか。
- [ ] [P1] 全体統計と局所エンティティ特徴を別経路で学習し、最後に結合できないか。
- [ ] [P1] **入力次元とパラメータ数を混同していないか**。共有エンコーダならエンティティ数が増えても重みは共有できる。
- [ ] [条件] 順序に意味がない集合は DeepSets / attention pooling、関係が重要なら GNN、空間格子なら CNN 等を比較したか。
- [ ] [条件] 変動長のカード・手札・盤上ユニットに対し、padding + mask / ragged な候補列を正しく処理したか。
- [ ] [条件] 将来性やルール固有の複雑な指標を**補助教師（auxiliary target）**で学習できないか。
- [ ] [条件] 表現の情報損失を調べるため、同じ集約特徴だが最適行動が異なる局面を抽出したか。

### 4.3 正規化と前処理

- [ ] [P0] ラベルと入力の桁が極端に違わないか。定数スケール・標準化・対数変換を比較したか。
- [ ] [P1] 枚数・HP・コスト等は**自然な上限で割る**など、本番にも適用可能な正規化を優先したか。
- [ ] [P1] 稀な巨大値や飽和値に対して log1p / clip / robust scaling を比較したか。
- [ ] [P1] 欠損・存在しないカードはゼロ埋めだけで区別できるか。**存在マスク**が必要ではないか。
- [ ] [条件] 訓練と推論の C++ / Python で浮動小数・丸め・順序・符号が一致するか回帰テストしたか。

### 4.4 ネットワークの選び方

- [ ] [P0] **線形モデル・小型 MLP・GBDT**を最初の比較候補に入れたか。
- [ ] [P1] パラメータ数・FLOPs より、**実測レイテンシ**と対戦性能を見ているか。
- [ ] [P1] 深さ・幅・残差接続・LayerNorm 等を、学習安定性と提出時コストの両面で比較したか。
- [ ] [条件] 相手と自分のカード群を同じ重みで処理するなど、**ゲームの対称性**を設計に入れられないか。
- [ ] [条件] Policy と Value の共有 trunk は省コストだが、**損失間の競合**が出ていないか。
- [ ] [条件] 明示的な評価関数 `h(s)` に対し `V(s)=h(s)+Δθ(s)` を学習する残差構成は有効か（スケールを揃える）。

## 5. 教師あり学習：Policy・Value・行動評価

### 5.1 目的変数を定義する

- [ ] [P0] `V(s)` は**勝敗期待値、勝率、得点期待値、得点差**のどれかを明示したか。
- [ ] [P0] `Q(s,a)` は、行動直後の値か、最適応答を含む将来報酬かを明示したか。
- [ ] [P0] 同じ局面でも**手番側視点**と固定プレイヤー視点が混ざっていないか。
- [ ] [P1] まず **MC リターン回帰**（終局結果を教師）と教師探索値回帰を比較したか。
- [ ] [P1] 勝率を使うなら calibration（予測 0.7 の局面が本当に約 70% 勝つか）を確認したか。
- [ ] [P1] 得点が重要なら、勝率だけでなく得点差回帰や複数 head にした方がよくないか。
- [ ] [条件] 価値の分布・分位点・WDL（勝ち/引分/負け）を学習すると、平均値だけより有用か。

### 5.2 模倣学習（Behavior Cloning）

- [ ] [P0] 教師の行動ラベルが合法か、教師時点の情報しか入力していないか。
- [ ] [P1] 教師の一手だけを正解にして、他の同等に良い手を誤って罰していないか。
- [ ] [P1] 教師の**訪問回数分布・行動価値分布**があるなら hard label ではなく soft target を使えないか。
- [ ] [P1] 教師と学習器の選択の一致率だけでなく、**行動差が終局結果へ与える損失**で評価したか。
- [ ] [条件] 自分の方策で到達した局面に教師を問い合わせて再学習する **DAgger** を検討したか。
- [ ] [条件] 教師の強さを超えたいなら、自己対戦 RL・探索改善・選択した手の反実仮想評価などを組み合わせたか。

### 5.3 ランキング・行動候補

- [ ] [P1] 巨大な固定 action head より、**合法手を列挙して `Q(s,a)` を採点**する設計の方が適さないか。
- [ ] [P1] 行動タイプ（召喚・攻撃・使用・パスなど）と引数（対象、位置）を**階層的に扱う**方が安くないか。
- [ ] [P1] 行動候補の選別は recall@k、選択 top-k の勝率、オラクル手の取りこぼしで測ったか。
- [ ] [P1] pairwise / listwise ranking と回帰を比較したか。**順位が重要な用途**では回帰誤差最小が最善とは限らない。
- [ ] [条件] Policy prior で上位候補を絞り、深い評価を行う**2段階推論**ができないか。
- [ ] [条件] 影響が局所的なアクションなら、候補ごとの埋め込みや中間特徴を使い回せないか。

### 5.4 損失関数

- [ ] [P0] 出力範囲と損失が対応しているか（確率→CE/BCE、実数→MSE/Huber、順位→ranking loss）。
- [ ] [P1] label noise が大きい場合、MSE より Huber 等が堅牢かを比較したか。
- [ ] [P1] サンプル数の多い局面・相手・フェーズが損失を支配していないか。
- [ ] [P1] 複数 head の損失重みを固定したまま、勾配スケールに大差が出ていないか。
- [ ] [条件] 下流の探索に使うなら、絶対的な平均誤差より**局所的な候補の順序・相対誤差**を計測したか。

## 6. TD 学習・価値反復・Q 学習

### 6.1 TD 方式と符号

- [ ] [P0] **価値の定義と Bellman ターゲット**を書き下したか。例：固定プレイヤー視点なら `r + γV(s')`、視点が交替する零和の無報酬局面では符号反転が必要。
- [ ] [P0] **同じプレイヤーが連続行動する場合、行動ごとに無条件で符号を反転していないか**。
- [ ] [P0] 終局では後続価値を 0 とし、勝敗報酬を重複加算していないか。
- [ ] [P0] 終局と時間打ち切りで価値を 0 とする条件が違うことを検証したか。
- [ ] [P1] **MC（高分散・低ブートストラップバイアス）vs TD(0)（低分散寄り・推定バイアス）**を比較したか。
- [ ] [P1] `n`-step return / TD(λ) / λ-return / GAE を検討したか。局面の先読み深さと推定誤差の折衷を取れる。
- [ ] [P1] TD target に使用するネットワークを、頻繁に変わるオンラインモデルから切り離す**target network / EMA**を比較したか。
- [ ] [P1] **1ステップの誤差が小さくても最終勝率が上がらない**ことを念頭に、リターン予測と勝率を併記したか。
- [ ] [条件] λ を手数、フェーズ、残りターン、推定不確実性で変える実験に価値はあるか。
- [ ] [条件] 中間報酬がある場合、報酬の単位・割引・勝敗とのトレードオフは一致しているか。

### 6.2 DQN 系・Q 値の問題

- [ ] [P1] 行動空間が固定で小さいか。**可変長・構造化アクション**なら DQN をそのまま使うのは難しい。
- [ ] [P1] `max_a Q(s',a)` の過大評価に注意し、Double DQN を比較したか。
- [ ] [P1] 大きな遷移相関に対して experience replay が有効か。最新データへの適応とのバランスを取ったか。
- [ ] [P1] まれな重要局面を見落とすなら PER（Prioritized Experience Replay）を比較したか。
- [ ] [条件] Dueling head、distributional Q、multi-step return 等は**個別に効果検証**したか。
- [ ] [条件] 観測から推定できない敵の状態が価値を左右する場合、履歴や belief 無しの Q 学習に限界がないか。

### 6.3 Offline RL の落とし穴

- [ ] [P0] **固定ログに無い行動の Q 値が過大評価**されないか。データ分布外行動の外挿に注意。
- [ ] [P1] BC / AWR（Advantage-Weighted Regression）等の単純な学習から比較したか。
- [ ] [条件] CQL / IQL 等の保守的な offline RL を検討する価値があるか（実装複雑度に注意）。
- [ ] [条件] offline で強い結果が出ても、最終的に**独立した実対戦**で改善を検証したか。

## 7. Policy Gradient / Actor-Critic / PPO / 自己対戦 RL

### 7.1 強化学習の立ち上げ

- [ ] [P0] 学習環境で**ランダム方策・固定方策・学習方策**が合法に最後まで対戦できるか。
- [ ] [P0] まず極小ゲーム（小さい盤、少ないカード、短いターン）で**過学習して意図通り勝てる**ことを確かめたか。

- [ ] [P1] PPO が必要か。強い教師があるなら BC + 探索、価値だけなら TD の方が安く試せるのではないか。

### 7.2 探索・報酬・行動の扱い

- [ ] [P0] 合法手 mask を softmax・サンプリング・logprob・評価の**全経路**に適用したか。
- [ ] [P0] パス・終了・行動不能・複数種類の対象選択などの特殊手が欠落していないか。
- [ ] [P1] advantage の正規化、GAE(λ)、entropy bonus、value loss の重みを記録しているか。
- [ ] [P1] PPO の ratio / clipping / KL / entropy が想定通りか。古い logprob を更新後のネットで計算し直していないか。
- [ ] [P1] 報酬を「とにかく密」にする前に、**本来の目的と違うものを最適化する reward hacking** を点検したか。
- [ ] [条件] 理論上の最適方策を保存したい場合、potential-based shaping `F(s,a,s') = γΦ(s') - Φ(s)` を検討し、前提（Markov 状態・終端等）を守ったか。
- [ ] [条件] 即時スコア、リソース差、勝利確率を補助 head として予測する方が、中間報酬の人為的変更より安全ではないか。
- [ ] [条件] 探索で選ぶ行動と PPO が学習する行動分布は一致しているか。off-policy の補正が必要ではないか。

### 7.3 安定性・効率

- [ ] [P0] 学習中の勝率だけでなく、**固定した旧バージョンとベースライン**への勝率を測っているか。
- [ ] [P1] 学習曲線とともに、policy entropy、KL、value loss、explained variance、勾配ノルムを記録したか。
- [ ] [P1] win-rate が崩れた時、過大な policy 更新／相手の非定常化／報酬の偏りを切り分けたか。
- [ ] [P1] rollout 速度・更新時間・GPU 使用率を可視化し、サンプル効率と wall-clock 効率を区別したか。
- [ ] [条件] 複数 worker のモデルが古くなる場合、方策の鮮度・off-policy 補正（V-trace など）を検討したか。
- [ ] [条件] 試合長が偏るなら、worker 間の待ち合わせ・バッチサイズ・途中保存を最適化したか。

## 8. AlphaZero：Policy + Value + MCTS

### 8.2 探索器の正しさ

- [ ] [P0] node が持つ値の**視点**（手番側／根プレイヤー側）を文書化し、親への backup と選択時の Q が一貫しているか。

- [ ] [P0] PUCT の `Q + U` の**スケール**が正しいか。`Q∈[-1,1]` なら探索係数もそのスケールで調整したか。
- [ ] [P0] 未訪問ノードの Q、訪問回数 0、全合法手 1 通り、パス、同点、引き分け、投了をテストしたか。
- [ ] [P1] root でのみ導入する探索ノイズ（Dirichlet 等）が**競技評価時には不要／調整対象**になっているか。
- [ ] [P1] self-play 用の**温度付き行動サンプリング**と、本番での決定的な選択を分離したか。

- [ ] [条件] 並列 MCTS の virtual loss や batching は、オーバーヘッドを測って導入したか。

### 8.3 自己対戦と学習ターゲット

- [ ] [P0] 保存するサンプルを **`(observation, π_search, z)`** と定義したか。`π_search` は訪問数等による探索分布、`z` は終局結果。
- [ ] [P0] value 教師 `z` は**その局面の評価視点**に変換したか。
- [ ] [P0] policy loss が探索分布と予測方策の CE / KL に対応し、非合法手の確率が混入していないか。
- [ ] [P1] 探索結果がいつも特定手に集中しすぎる／いつも一様になるとき、シミュレーション数・温度・prior を点検したか。
- [ ] [P1] 学習データの生成に使ったモデルバージョンと、更新後モデルを管理できるか。
- [ ] [P1] 新モデルの採用判断を**相互対戦だけでなく固定相手プール**で行っているか。
- [ ] [条件] MCTS policy の教師がノイズで汚れているなら、探索用行動選択と**学習用ターゲット**を分けて設計できないか。
- [ ] [条件] 新モデルで旧局面を再探索する **reanalysis** がデータ生成コストを下げられるか。

### 8.4 少ない探索予算に向けた工夫

- [ ] [P1] `0/1/4/8/16/...` 回の探索予算で勝率を測定し、**「MCTS を使う価値が生じる閾値」**を調べたか。

- [ ] [条件] 逐次の policy 推論を減らし、**value による再ランキング**や候補ごとの簡易 rollout の方が速くならないか。
- [ ] [条件] 探索結果を学習して得た **policy-only** を提出し、探索はオフラインに寄せられないか。

## 11. 不完全情報・確率イベント・同時行動

### 11.1 情報集合と belief

- [ ] [P0] **内部状態 `s` とプレイヤーが観測できる情報集合 `I` を混同していないか**。
- [ ] [P0] 自分の行動決定に、相手の非公開手札・山札順序・未来の乱数を使っていないか。

- [ ] [P1] 単一の隠れ状態推定値を「真実」として先読みしていないか。複数サンプルによる頑健性は必要か。

- [ ] [P1] 一度見たカードが戻らない等の**公開履歴から得られる情報**を特徴に入れたか。
- [ ] [条件] 厳密な belief 更新が重いなら、履歴集約、カード残数推定、RNN / Transformer 等で近似できないか。

### 11.2 不完全情報での探索の罠

- [ ] [P0] **完全状態を決め打ちする determinization** では、「実際には区別できない未来ごとに別の戦略を選べる」**strategy fusion** が起き得ると理解したか。
- [ ] [P1] determinization ごとの最適手の単純平均が、情報獲得・ブラフ・相手の反応を正しく評価しない局面を点検したか。
- [ ] [条件] IS-MCTS / RIS-MCTS 等の情報集合を意識した探索を比較したか（手法ごとの前提を検証する）。
- [ ] [条件] chance node は「自分が選べる分岐」ではない。**確率に応じた期待値**でバックアップしているか。
- [ ] [条件] 同時行動なら、単純な順番付き minimax に変換して一方に不当な情報を与えていないか。
- [ ] [条件] 相手の行動を観測した後の選択と、観測前の選択を探索木で区別したか。

### 11.3 CFR / Deep CFR / ReBeL / NFSP

- [ ] [P1] **2人零和・不完全情報・競争的な駆け引き**なら、CFR 系を候補に含めたか。
- [ ] [P1] 小さい抽象化ゲーム／部分ゲームで**tabular CFR / MCCFR**を動かし、到達すべき基準を作ったか。
- [ ] [P1] regret、平均戦略、現在戦略を区別して記録したか。CFR の反復方策と最終平均戦略を混同していないか。
- [ ] [条件] 情報集合が非常に大きい場合は Deep CFR / SD-CFR を検討したか。サンプル効率と関数近似誤差に注意。
- [ ] [条件] **反実仮想 regret に必要な相手・chance reach の重み**が正しいか。単なる self-play の TD 誤差を regret と呼んでいないか。
- [ ] [条件] NFSP の平均方策学習では、リザーバサンプリングと best-response 用データの違いを理解しているか。
- [ ] [発展] ReBeL のような**public belief state 上の探索**が実装コストに見合うか。
- [ ] [発展] 大規模不完全情報ゲームでは均衡近似と相手 exploit を明示的に分けて運用するか。

> **重要**：AlphaZero の成功を「自己対戦＋NN＋MCTS なら不完全情報も同様に解ける」と一般化しない。ゲーム構造に適した計画・均衡学習が必要。

## 13. 学習の安定化・汎化・デバッグ（一般 ML / Kaggle）

### 13.1 過学習と学習不足を分ける

- [ ] [P0] **train loss / validation loss / 対戦勝率**を別々に記録したか。
- [ ] [P0] train loss が下がらないなら、入力の不備・教師のノイズ・モデル容量・学習率・実装バグを順に疑ったか。
- [ ] [P0] train だけ良いなら、データ数・相関・分割方法・正則化・特徴リークを検証したか。

- [ ] [P1] 正則化（weight decay、dropout、データ拡張、early stopping）を、症状に応じて個別に比較したか。
- [ ] [P1] 特徴量を減らすより、共有表現や適切な inductive bias（CNN/GNN 等）で**学習しやすい構造**を与えられないか。
- [ ] [P1] データが多いほど良いと決めつけず、**古い弱いモデルが生成したデータの比率**を調整したか。
- [ ] [条件] 同じ loss でも性能が異なるなら、モデルの予測 calibration / ranking / OOD 挙動を比較したか。

### 13.2 最低限の学習ログ

- [ ] [P1] モデルの予測平均・分散・端点への張り付き・勾配 norm・重み norm を見ているか。
- [ ] [P1] **constant prediction**（ほぼ同じ値しか予測しない）や、policy の 1 アクションへの崩壊を監視したか。
- [ ] [P1] 勾配クリッピング・適切な初期化・optimizer・学習率 scheduler を比較したか。

- [ ] [条件] AMP / bf16 / fp16 を使うなら、損失スケールと数値安定性、GPU 実効速度を測ったか。
- [ ] [条件] 独立した複数学習 seed で良し悪しが再現するか。最良の 1 seed だけを比較していないか。

### 13.3 Kaggle 的な改善ループ

- [ ] [P0] **何を変えたか・仮説・測定指標・結果**が1実験1レコードになっているか。
- [ ] [P0] validation が上がったのに試合で弱いなら、**代理指標とのズレ**を分析したか。
- [ ] [P1] エラーを得点差・ターン数・先後・ユニット数・カード種・相手戦型ごとに切り分けたか。
- [ ] [P1] 単純なベースラインで学習を回してから複雑な特徴・構造を足したか。
- [ ] [P1] 複数の特徴セットを ablation して、実際に有効な情報を確認したか。
- [ ] [P1] **OOF（out-of-fold）予測**で教師モデルの誤差解析・stacking をしたい場合、試合グループ単位の fold を守ったか。
- [ ] [条件] ensemble で勝率が上がるか。ただし提出時の推論コストと見合うか。
- [ ] [条件] ensemble を単一モデルに**知識蒸留**して、同程度の強さを低コストで出せないか。
- [ ] [条件] validation に何十回も適応した場合、別 holdout での確認が必要だと理解しているか。

- [ ] [条件] 未知カード・新しい盤面・低頻度条件への性能を、特定の難しいケースだけで測定したか。

## 17. 典型的な症状 → 最初に疑うこと

| 症状 | 最初に疑う原因 | 次の実験 |
|---|---|---|
| train loss すら下がらない | 入力・ターゲットのずれ、符号バグ、学習率、容量不足 | 極小データ暗記、単純問題の再現 |
| train は良いが validation が悪い | リーク／分割ミス、過学習、分布の偏り | 試合単位 split、特徴削減ではなく共有化／正則化 |
| validation は良いが弱い | 代理指標不一致、教師の偏り、探索との相性 | 対戦ログ分析、候補ランキング、arena 勝率 |
| 自己対戦で伸びたが旧 bot に負ける | 非推移性、忘却、局所 exploit | 過去世代の再学習、相手プール評価 |
| PPO が突然崩壊 | 学習率／KL／報酬スケール／非定常な相手 | policy entropy・KL・advantage・サンプル世代確認 |
| TD が発散・極端な値 | target drift、Q 過大評価、符号／終局バグ | target network、Double Q、報酬と Bellman のテスト |
| MCTS を深くしても弱い | value 視点ミス、prior の偏り、探索コスト過大 | 真の小問題で検証、PUCT を外す、NN なしとの比較 |
| 一部の戦型に極端に弱い | 分布外、データ欠損、戦型の偏り | 戦型別成績、異種相手学習、hard-case sampling |
| テストで早くても提出で落ちる | 初期化／I/O／最大ケース／モデル埋め込み | 同一 C++ ビルド、p99、境界条件、時間安全余裕 |
| モデルを大きくしても伸びない | 教師信号不足、特徴情報不足、データ生成律速 | 補助教師、強い教師探索、データ生成速度の改善 |

- [ ] **線形／GBDT／小型 MLP**で局面価値 `V`、または行動優先度 `Q` を教師あり学習。
- [ ] 学習器のみ・探索のみ・組み合わせの3条件で勝率比較。
- [ ] 軽量 C++ 推論への移植、時間−勝率曲線を確認。

### Phase 2：教師の質・探索への接続

- [ ] 強い探索器で作ったラベルを追加し、MC outcome と比較。
- [ ] `V(s)` 回帰 vs 行動ランキング vs Policy を比較。
- [ ] データが不足する戦型や局面を重点生成。
- [ ] 探索結果を学習へ戻す **policy/value distillation** と DAgger を検討。

### Phase 3：TD 学習・自己対戦

- [ ] MC、TD(0)、n-step、TD(λ) を同一特徴・同等計算予算で比較。
- [ ] 過去 bot + 強い固定 bot + 異種 bot の対戦相手プールを作る。
- [ ] 世代ごとの勝率行列を保存し、忘却・循環を検出。
- [ ] 新方策による局面を再収集し、分布ずれを減らす。

### Phase 4：AlphaZero 系（ゲームが適する場合）

- [ ] Policy + Value + MCTS の単体テストと極小ゲームでの検証。
- [ ] 低 visit の PUCT、Gumbel 系、NN なし探索を比較。
- [ ] KataGo 的な探索予算配分・補助教師を個別に試す。
- [ ] 学習効率（対局生成時間）と提出効率（推論制約）の双方を比較。

### Phase 5：問題固有の発展

- [ ] 不完全情報なら belief / IS-MCTS / CFR 系を小さな抽象化ゲームで比較。
- [ ] 多様性が足りなければ league / PFSP / PSRO を検討。
- [ ] モデルが遅ければ蒸留・NNUE 的差分・量子化を検討。
- [ ] 大規模モデル学習や MuZero は、明確な利点が見えてから採用。

**私なら最初に試す順番**：`(A) 強い既存探索器でラベル収集 → (B) 小型 value / ranking モデルを教師あり学習 → (C) 探索へ組み込み、同時間の勝率測定 → (D) 自己対戦 + TD(λ) → (E) population self-play → (F) ゲーム特性に合えば AlphaZero / Gumbel / CFR 系`。

## 21. 最後の確認：何を最優先にするか

- [ ] **実戦で計測できていない改善を採用しない。** validation loss が良いだけでは弱い可能性がある。
- [ ] **教師・観測・ルールが正しいか**を、ネットワークを複雑化する前に疑う。
- [ ] **推論時間を含めた強さ**を最適化する。ネットが強くても探索回数が激減すれば総合性能は下がり得る。
- [ ] **未知の相手に強いか**を確認する。自己対戦で五分という事実には情報がほぼない。
- [ ] **最強手法の名前を目標にしない。** 既存探索・学習済み value・少数 visit MCTS・CFR 系を、ゲームの性質と実測で選ぶ。
