# AHC / CodinGame ヒューリスティック探索 Tips チェックリスト

> **目的**：AHC（AtCoder Heuristic Contest）や CodinGame の Bot Programming で、解法設計・探索・評価・高速化・検証の際に見返すチェックリスト。
>
> **使い方**：問題に関係する項目だけを確認する。各項目は「常にやるべきこと」ではなく、改善の仮説を作るための観点。**実測して効果が出たものだけ採用**する。
>
> **記号**：`[基本]` まず検討 / `[条件]` 成立条件がある / `[発展]` ボトルネックや問題特性が合う場合に検討。
>
> **最終更新**：2026-10-29。第5章の定数倍高速化を、CPU・キャッシュ・コンパイラ・SIMD・計測まで再構成。

## 0. 最初に確認する10項目

- [ ] **どのケースで弱いか**を分類したか。平均スコアだけでなく、失敗パターン・下位ケース・初期シード依存を見たか。
- [ ] 「何を決めれば、残りは厳密に・貪欲に・高速に決まるか」を考えたか。
- [ ] 状態の表現や制約が、そもそも良い解を排除していないか。
- [ ] 探索の対象・順序・近傍・初期解を見直したか。評価関数だけで解決しようとしていないか。
- [ ] 評価関数に、真のスコア・将来性・自由度・制約違反を適切に反映できているか。
- [ ] 同一状態・実質同じ状態・無意味な遷移の探索を減らせないか。
- [ ] 差分計算・局所更新・前計算・枝刈りによって、**有効な探索回数**を増やせないか。
- [ ] 時間の使い方（序盤の探索／終盤の詰め／多スタート／再加熱）は適切か。
- [ ] ベースラインと同じ条件で比較し、複数シード・ケースで改善を確認したか。
- [ ] 最後に合法性・時間制限・メモリ制限・入出力・実行環境を検証したか。

## 1. 問題分析・解法設計

### 1.1 弱点の特定・問題の分解

- [ ] [基本] **自分の解法が下手なケース**を具体的に列挙する。何がボトルネックか（配置不能、局所解、時間不足、将来価値の過小評価など）を分ける。
- [ ] [基本] 何かを固定したときの**厳密解・最適戦略・部分最適解**を考える。
  - [ ] その判断の中で「必須の要素」と「なくてもよい要素」を分離する。
  - [ ] ある部分を厳密に解けるなら、その部分を探索変数から外せないか。
- [ ] [基本] 問題を、探索しやすい部分問題に分割できないか。
- [ ] [基本] 探索順序を変えた方がよくないか。重要／制約が厳しい／後戻りしづらい決定を先に処理できないか。
- [ ] [条件] 容易に最適化できる領域と、局所解から抜けづらい領域を分ける。後者には大きな近傍・多スタート・再構築を使う。
- [ ] [条件] 実現可能性の判定問題に落とせないか。目的値を固定して「その値を達成可能か」を解く方法もある。

### 1.2 状態空間の設計

- [ ] [基本] **状態表現が最適解を含み得るか**を確認する。根拠のない強い状態制限は、評価精度の改善より優先して緩和する。
- [ ] [基本] ある変数を決めると他の変数が最適／準最適に決まるなら、決まる側を探索から取り除く。
- [ ] [基本] 最後に安く微調整できる変数は、主探索に含めないことを検討する。
- [ ] [基本] 同一視できる状態・対称な状態・履歴だけ異なる状態を削減できないか。
- [ ] [条件] 無駄な中間状態を経由せずに、有望な状態へ直接遷移できる表現・操作に変える。
- [ ] [条件] 一部の値をパラメータ化した貪欲法・構築法を作り、その**パラメータを探索**できないか。
- [ ] [条件] 構築順序そのものを探索対象にする／逆順から構築する／デコーダを変える、といった別表現も試す。

### 1.3 探索の量・質・多様性

- [ ] [基本] 同じ状態を再探索しない。ハッシュ、正規化、訪問フラグ、履歴等を使う。
- [ ] [基本] 明らかに悪い状態・意味のない遷移を避け、**有効な遷移の割合**を増やす。
- [ ] [基本] 計算量を下げ、同じ時間で試せる候補数を増やす。
- [ ] [基本] 似た状態にばかり集中しないよう、多様性を確保する。
- [ ] [条件] 近傍を局所に限定しすぎていないか。探索空間が分断されていないか。
- [ ] [条件] 大域的な変更、複数変数の同時変更、破壊と再構築を導入する。

## 2. 評価関数・将来価値

### 2.1 評価対象と特徴量

- [ ] [基本] 真の最終スコアとの関係を確認する。代理評価を最適化しても本番スコアが上がらない問題に注意。
- [ ] [基本] **局所情報で評価**できないか。隣接関係、次数、連結性、局所的な密度などを使う。
- [ ] [基本] **将来の行動の自由度**を評価する。次の合法手数、空き領域、選択肢の広さ、残存資源など。
- [ ] [条件] 将来スコアの期待値を推定する。確率分布、到着頻度、相手の応答を近似する。
- [ ] [条件] 一部の制約を無視した「楽観的に最適行動した場合」の値を、将来性の評価や上界に使う。
- [ ] [条件] 転倒数・最長増加部分列（LIS）など、目的に合う構造指標を特徴量にする。
- [ ] [条件] これまでの行動履歴／採択された部分状態をカウントして、評価・候補生成に利用する。
- [ ] [基本] 同点が大量に発生する場合は**タイブレーク**を設計する（余裕・自由度・乱数など）。

### 2.2 複数の評価軸を組み合わせる

- [ ] [基本] 主目的と副目的を区別する。異なる目的の行動を、無理に同一のスカラー評価へ押し込まなくてもよい。
- [ ] [条件] **辞書式（タプル）** `(a, b)`：`a` 最優先、同点時だけ `b`。簡便だが `a` の微小改善が `b` の大損失を無視する。
- [ ] [基本] **加算** `w_a a + w_b b`：主評価＋ボーナス／ペナルティの基本形。各項のスケールに注意。
- [ ] [条件] **乗算** `a * b`：両方重要で一方が低いと厳しい状況に使う。ただし符号やゼロに注意。
- [ ] [条件] `min` / `max` やボトルネック指標は、滑らかな代理評価（softmin / softmax、近似ペナルティなど）に変えられないか。
- [ ] [条件] 固定和のとき `x+y` と `x²+y²` では好む分布が変わる。**二乗和は偏りを好む**ため、集中を評価したいのか均等化したいのか確認する。
- [ ] [条件] 「全体に少しずつ悪い状態」が後から修復しやすい場合がある。局所的な致命傷と、分散した軽微な損失を区別する。

### 2.3 評価の形を変える・段階的に精緻化する

- [ ] [条件] 探索初期は改善しやすい粗い評価を使い、時間の経過とともに真の評価に近づける。
- [ ] [条件] 複数の評価指標があるなら、初期解構築フェーズと本探索フェーズで別の評価を使う。
- [ ] [条件] 制約違反をペナルティ化し、探索が進むにつれてペナルティを強める。
- [ ] [条件] 評価差の分布が極端な場合、単調変換した評価で探索する。例：非負スコア `s` に対して `sqrt(s)` を使う。
- [ ] [基本] 評価関数を変えたら、**温度・受理率・近傍の振幅**も再調整する。
- [ ] [基本] 評価値の絶対量だけでなく、候補間の**差分の分布**を観測する。

> **注意**：`sqrt` のような単調変換は最大点を保存しても、焼きなましの受理確率は変わる。`softmin` / `softmax` は近似であり、真の `min` / `max` と最適解が一致するとは限らない。

## 3. 焼きなまし（Simulated Annealing）

### 3.1 探索空間・初期解

- [ ] [基本] まず**簡単な状態表現＋小さな近傍＋高速な差分評価**で強いベースラインを作る。
- [ ] [基本] 探索状態を減らす。決定的に最適化できる変数、最後に微調整できる変数を除く。
- [ ] [条件] 貪欲構築や別の簡単な目的で初期解を作ってから、本目的の焼きなましに移る（二段階 SA）。
- [ ] [条件] 探索しやすい代理問題を最適化し、解を元問題へ戻す。
- [ ] [条件] パラメータ化した貪欲法を焼きなましで調整する。

### 3.2 有効解を作りにくいとき

- [ ] [基本] 少なくとも合法な近傍だけで乱択山登りが成立するか調べる。
- [ ] [条件] `kick → 修復（有効解化）` をひとつの大きな近傍として扱う。
- [ ] [条件] 非合法状態を許して、制約違反をペナルティとして評価関数に組み込む。
- [ ] [条件] **判定問題化**：目標値 `N` の解を得たら、それを初期解として `N+1` を狙う。
- [ ] [条件] 必ず有効解を生成するデコーダや操作に状態表現を変更する。
- [ ] [基本] 有効解の作りやすさと、探索空間の到達可能性のトレードオフを確認する。

### 3.3 温度・受理判定

- [ ] [基本] 温度の開始値・終了値を、実際の**スコア差分の分布と受理率**から調整する。
- [ ] [条件] 非線形な冷却スケジュールを試す。例：時間比率 `t ∈ [0,1]` に対して `T(t) = T0 * (T1/T0)^(t^1.5)`。
- [ ] [条件] スコアを非線形変換した場合、温度スケジュールも対応して調整する。
- [ ] [条件] 早期に収束すると危険な問題では、終盤まで一定の多様性・非改善遷移を維持する。
- [ ] [発展] 受理判定を対数形にする（最大化で `Δ = new_score - old_score`）。

```cpp
// u は (0, 1] の一様乱数、T > 0。最大化の SA。
// Δ >= 0 なら必ず受理される。
const bool accept = (delta >= temperature * std::log(u));
```

- [ ] [発展] `log(u)` がボトルネックなら、対数乱数をテーブル化して近似的に使う。

```cpp
// 65536要素の例。乱数テーブルの近似分布に基づく判定。
// 初期化時にシャッフルしてもよい。
for (int i = 0; i < 65536; ++i) {
    log_table[i] = std::log((i + 0.5) / 65536.0);
}
// 毎回 log() を呼ばずに使う（rng() は十分品質のよい乱数を想定）。
const bool accept = (delta >= temperature * log_table[rng() & 65535]);
```

- [ ] [発展] **焼きなましの受理判定を利用した枝刈り**：受理に必要な閾値を先に決め、スコア増分の上界が閾値に届かないと分かったら途中で評価を打ち切る。
- [ ] [基本] 受理率だけでなく、最良値の更新頻度、現状態と最良状態の差、時間帯別の改善量を見る。

> **注意**：上の対数式は `T > 0`・`u > 0` を前提とする。`T = 0` では山登り判定に切り替える。対数テーブルは厳密な連続一様乱数の代用ではなく近似。乱数の下位ビットを使うなら、その品質も確認する。

### 3.4 多スタート・停滞対策・終盤

- [ ] [条件] **多スタート**を試す。異なる初期状態・構築順・パラメータを使う。
- [ ] [条件] これまでの最良解を初期解として再探索する。再開するたびに初期温度を下げる案もある。
- [ ] [条件] **Successive Halving**：複数の初期解／決め打ちパラメータ候補に短時間ずつ与え、成績が悪い候補を段階的に打ち切る。
- [ ] [条件] 最良スコアが一定期間更新されなければ、`best_state` へ**ロールバック**する。
- [ ] [条件] 現状態が `best_state` から悪化しすぎたら、ロールバック／再加熱／kick を試す。
- [ ] [条件] 終盤ほどロールバックを積極的にして、最良解の周辺を集中的に探索する。
- [ ] [条件] 終盤は同じ近傍で山登り、または小さな部分問題ごとの SA で詰める。
- [ ] [条件] スコア分散が高い場合、未収束・多峰性・初期解依存・ケース差を切り分ける。

### 3.5 近傍：サイズと到達可能性

- [ ] [基本] **小さい近傍**から考える。少ない変数しか動かさず、差分評価しやすい操作を優先する。
- [ ] [条件] **大きい近傍**を用意する。部分破壊＆再構築、`kick → 山登り`、複数点 swap など。
- [ ] [条件] 時間経過に応じて近傍を徐々に小さくし、終盤の微調整を強める。
- [ ] [条件] 同時に評価の精度を上げ、近傍のサイズとの整合を取る。
- [ ] [基本] 近傍によって到達できない状態が生まれていないか確認する。
- [ ] [条件] 逆順構築など、探索順だけ異なる近傍を追加する。似た近傍でも補完的な役割があり得る。

### 3.6 近傍：選び方・候補の質

- [ ] [基本] 近傍の**選択分布**を意識する。頻度の高い操作が偶然過大評価されていないか。
- [ ] [条件] 近傍 A に `a` 通り、B に `b` 通りの候補があるなら、候補全体から一様に選ぶ基準では `a:b` の比率で操作種類を選ぶ。
- [ ] [条件] 操作種類・候補を、パラメータで重み付けして偏らせる。必ず無偏り基準と比較する。
- [ ] [条件] 候補が多い場合は乱択のみでなく、順番に走査する／巡回して全体をカバーする。
- [ ] [基本] **スコアに影響しない近傍**は除外する。無意味な試行をしない。
- [ ] [条件] 現在の worst な箇所、制約違反が強い箇所、改善の余地が大きい箇所を重点的に変更する。
- [ ] [条件] 直近で変更した位置の周辺など、改善しやすい候補を優先する。
- [ ] [条件] 良い候補を多重に登録した `cand` 配列を前計算し、ランダムサンプリングする。
- [ ] [条件] 候補を複数個ランダム生成し、**軽量評価**で最有望候補を選んでから詳細評価する。
- [ ] [条件] 過去に採択された部分状態を集計し、成功頻度を候補重みの参考にする。

> **注意**：候補全体から一様に選ぶことは「無難な初期設定」だが、必ず最善ではない。状態依存・非対称な提案分布は、通常の SA の理論的な分布を変える（厳密なサンプリングが目的なら Metropolis–Hastings 補正が必要）。最適化目的なら有効性を実験で判断する。

### 3.7 近傍：内部探索・部分最適化

- [ ] [条件] 近い状態が既に試されているなら、同様の候補を再探索せず新しい領域へ移る。
- [ ] [条件] 近傍の中で最良を選ぶだけでは局所解に陥るなら、評価に微小な乱数を足す。
- [ ] [発展] **n 点 swap などを DFS で探索**し、複雑な近傍から有望な遷移先を探す。
  - [ ] 分岐数・深さ・展開ノード数を制限する。
  - [ ] 一箇所への固執を避けるため、分岐を複数に振り分ける。
  - [ ] 時間が進んだら探索深さや展開ノード数を増やす案も試す。
  - [ ] 改善可能な上界を使い、悪くなりすぎた部分木を枝刈りする。
- [ ] [条件] 遷移後に影響箇所だけ局所的な最適化・山登りを実施する。
- [ ] [条件] **近傍候補を全列挙**できるなら、増分 `Δ` ごとに `cand[Δ]` へ格納してサンプリングする（整数で狭い範囲の場合など）。
- [ ] [発展] 前方・後方累積、遅延評価、連続区間への更新などを組み合わせ、近傍評価を高速化できないか。連結成分の更新でも同様の構造が使えることがある。
- [ ] [条件] `kick` は通常の受理判定を無視した大きなランダム変更として設計し、その後に修復や再探索を組み合わせる。

> **要検証メモ**：「両端から累積を取り、遅延評価と連番化により `O(N)` を `O(1)` にする」という元のアイデアは、**更新・問い合わせの具体的条件次第**。一般の連結成分更新まで常に `O(1)` になるわけではないので、適用可能な場面を個別に検討する。

## 4. ビームサーチ

- [ ] [基本] **同一視できる状態**を重複排除する（完全同一、対称性を除いた同一、評価に必要な情報が同じ状態など）。
- [ ] [基本] 似た状態がビームを占有しすぎないように、多様性を制約する。
  - [ ] 例：同じ特徴を持つグループの採用数を `WIDTH / k` 以下に制限する。
  - [ ] ただしグルーピングが粗すぎると最適解を落とすため、強さを調整する。
- [ ] [条件] スコアへ乱数や Gumbel ノイズなどを加えて探索の偏りを変える。
- [ ] [条件] 時間制限に合わせて**ビーム幅を動的調整**する。初期試行から必要計算量を見積もる。
- [ ] [条件] 木上のビームサーチを検討する： [rhoo「木上のビームサーチ」](https://qiita.com/rhoo/items/2f647e32f6ff2c6ee056)。
- [ ] [条件] 単純な即時評価では先が見えない場合、軽いロールアウトや将来価値を比較に使う。
- [ ] [基本] ビーム幅を増やすだけでなく、**状態の質・評価関数・重複排除・候補生成**を見直す。

## 5. 実装高速化（C++中心）

> **基本方針**：優先順位は **(1) 不要な計算を消す → (2) メモリアクセスを減らす／局所化する → (3) CPU が並列実行しやすい形にする → (4) 命令やライブラリを特殊化する → (5) 計測で採否を決める**。定数倍高速化の目標はベンチマークの数字そのものではなく、制限時間内に実行できる**有効な探索**の増加。
>
> **2026年版の注意**：2024年の [tatyam「定数倍高速化の技術」](https://speakerdeck.com/tatyam_prime/ding-shu-bei-gao-su-hua-noji-shu) を参照したが、講義に登場する特定の CPU、命令レイテンシ、当時の AtCoder コンパイラ設定は**固定の事実として転用しない**。CPU／コンパイラ／ターゲット ISA／コンテスト／言語選択ごとに再確認する。

### 5.1 アルゴリズム・計算量の削減（まずここ）

- [ ] [基本] **差分計算**できないか。全体評価 `O(N)` を局所更新 `O(1)`／`O(k)` にできないか。
- [ ] [基本] 前回の計算結果を**再利用**できないか。変更した領域だけ再計算する。
- [ ] [基本] 距離、三角関数、対数、候補集合、遷移表などを**前計算**できないか。テーブルサイズとキャッシュのトレードオフも測る。
- [ ] [条件] よく現れる部分状態／クエリだけをキャッシュし、過大なテーブルを作らない。
- [ ] [基本] **軽い評価 → 重い評価**の二段階選別を行えないか。
- [ ] [基本] **枝刈り・早期終了**：上界に達した、十分な解が見つかった、勝ち目がなくなった時点で打ち切る。
- [ ] [基本] 不要な処理を止める。例：MST の木が完成したら残りの辺を見ない。
- [ ] [条件] スコアの上界・下界を段階的に更新し、焼きなましの受理不可能性を早期判定する。
- [ ] [条件] ランダム探索中の判定に過剰に精密な計算／汎用データ構造を使っていないか。近似・単純化・遅延計算に置き換える。
- [ ] [基本] 条件判定の順序を考える。**安い・高確率で打ち切れる条件**を先に試す（副作用や仕様に注意）。
- [ ] [基本] 最適化対象が全実行時間に占める割合を確認する。ホット部分以外を速くしても効果は限定的（Amdahl の法則）。
- [ ] [条件] その高速化で**近傍の質・選択分布・探索順序**が変わるなら、単純な速度比較だけでなく最終スコアを測る。

### 5.2 メモリ管理・データ配置・初期化削減

- [ ] [基本] ホットループ内で動的確保・解放をしない。配列・作業領域を事前確保し**再利用**する。
- [ ] [基本] 小さな `vector`・木ノード・リスト要素を大量に個別確保していないか。確保回数とメモリ断片化を減らす。
- [ ] [基本] 上限が既知なら静的配列／`std::array` を、動的サイズなら容量確保済みの `std::vector` を検討する。`vector` の**要素アクセス自体**が遅いわけではない。
- [ ] [基本] 多次元座標・グリッドを一次元化できないか（例：`id = y * W + x`）。`vector<vector<T>>` より連続領域を優先する。
- [ ] [基本] ポインタを追うデータ構造より、添字で辿れるコンパクトな配列を検討する（BFS キュー、木、状態プール）。
- [ ] [条件] 小さな整数型（`uint8_t` / `uint16_t` / `int32_t`）へ詰められないか。キャッシュには有利だが、値域・符号・拡張コストを確認する。
- [ ] [条件] `struct` を丸ごとコピーしていないか。大きな状態は差分更新・軽い参照・変更ログ＋巻き戻しへ置き換えられないか。
- [ ] [条件] **AoS（構造体配列）/ SoA（フィールド別配列）**を、ホットループが使うフィールドの組で選ぶ（SoA は一部フィールドだけ読む／SIMD 化する場合に有利）。
- [ ] [条件] **Arena / bump allocator** を使い、最初に大きな領域を確保して線形に切り出せないか。標準では `std::pmr::monotonic_buffer_resource` も候補。
  - [ ] arena の寿命、アラインメント、上限超過、オブジェクトのデストラクタ、`release()` 後の参照無効化を確認する。
  - [ ] **一括解放・再利用**を優先し、「故意のメモリリーク」は短命・許容メモリ内・終了時回収が明確なケースに限定する。
- [ ] [条件] 独立の小さな領域を頻繁に作るなら、ワークスペースの再利用やサイズ別 pool / freelist を比較する。
- [ ] [条件] BFS キューは `head` / `tail` の単純な連続配列で十分か。リングバッファ不要なら `% capacity` も避けられる。
- [ ] [基本] **毎回 `fill` / `memset` する代わりに世代番号**で visited / dist / 一時マークを管理する（Fast-Clearing Array）。
- [ ] [条件] `IndexSet` / sparse set などで要素の追加・削除・列挙を高速化し、`clear` を実質 `O(1)` にできないか。
- [ ] [条件] 巨大な局所配列をスタックに置いていないか。スタックサイズ、ゼロ初期化、配置先を確認する。

#### Fast-Clearing Array の実装例

```cpp
struct EpochVisited {
    std::vector<uint32_t> mark;
    uint32_t epoch = 1;

    explicit EpochVisited(int n) : mark(n, 0) {}

    // 次の探索用に「全未訪問」へ切り替え。通常 O(1)。
    void clear() {
        ++epoch;
        if (epoch == 0) {  // uint32_t は周回する
            std::fill(mark.begin(), mark.end(), 0);
            epoch = 1;
        }
    }

    // 新たに訪問済みにした場合だけ true。
    bool visit(int v) {
        if (mark[v] == epoch) return false;
        mark[v] = epoch;
        return true;
    }
};
```

> **補足**：世代番号で距離も管理する場合は、`mark[v] != epoch` のときの旧 `dist[v]` を未初期化・無効値として扱う。`uint32_t` の世代が周回した際の全リセットも省略しない。大きな配列の型縮小では、オーバーフローや整数昇格を検証する。
>
> 参考：[IndexSet](https://topcoder-tomerun.hatenablog.jp/entry/2021/06/12/134643) / [初期化しない BFS・ダイクストラ](https://topcoder-tomerun.hatenablog.jp/entry/2022/11/06/145156)

### 5.3 CPUマイクロアーキテクチャ（Latency / Throughput / ILP）

- [ ] [基本] ホットループが**命令レイテンシ律速**か、**スループット律速**か、**メモリ律速**かを区別する。
  - *Latency*：ある命令の結果を後続命令が使えるまでの遅延（クロック）。
  - *Throughput*：独立した同種命令を継続投入できる速度。表では「1命令あたりの逆スループット（クロック）」のこともある。
- [ ] [基本] **ループの依存関係（critical path）**を探す。例：`s = f(s)` は逐次依存、`a[i] = f(b[i])` は要素ごとに独立しやすい。
- [ ] [条件] 独立したアキュムレータ・候補評価を複数本に分け、**ILP（命令レベル並列性）**を増やせないか。順序を変えてよい演算か確認する。
- [ ] [条件] CPU の **Out-of-Order実行、レジスタリネーミング、パイプライン**が効くように、ポインタ依存や逐次的な読み込みを減らす。
- [ ] [条件] 予測困難な分岐を減らす。条件付き加算・`cmov`・マスク処理が速いか比較する。**分岐を消せば常に速いわけではない**。
- [ ] [条件] `if` の順序を変えられるか。予測しやすさと、短絡による平均計算量の両方を考慮する。
- [ ] [条件] ループアンローリングや定数回のループ化で命令並列性・分岐回数を改善できるか。**コードサイズ、命令キャッシュ、レジスタ圧迫**で逆効果にもなる。
- [ ] [条件] 番兵を置き、探索や境界チェックに必要な分岐を減らせないか（番兵領域の確保と正当性をチェック）。
- [ ] [条件] 再帰→明示スタック、仮想関数・間接呼び出し→静的ディスパッチ、小関数のインライン化を試す。ただしコンパイラが既に処理している可能性がある。
- [ ] [条件] 乗除算のコストをターゲット CPU で確認する。**整数除算は一律に何クロックと決めつけない**（幅・符号・CPU 世代・依存性で変わる）。
- [ ] [条件] `%` / `/` の除数が**コンパイル時定数**なら、コンパイラが乗算・シフトへ置換していないか確認する。ソースコードを複雑に書き換える前に生成コードを見る。
- [ ] [条件] 周期が 2 の冪の**非負／unsigned**の剰余は `x & (mod - 1)` を検討できる。負数の剰余や一般の除数に無条件で適用しない。
- [ ] [発展] 除数が可変かつ多数回使用されるとき、逆数乗算（libdivide 等）や厳密な剰余専用化を検討する。浮動小数点による整数除算の代用は**丸め誤差と補正処理**の証明・検証なしに使わない。
- [ ] [条件] 特定の数学関数・汎用APIを、必要な精度・値域に限定した計算へ置き換えられないか（`hypot`、距離の平方、オーバーフロー安全な差分など）。
- [ ] [条件] **乱数生成器が律速**なら、PCG32 の高速バリアントや xoshiro 系などを比較する。生成コストだけでなく、シード再現性・下位ビットの品質・候補選択の偏りも確認する。
- [ ] [条件] **ビット演算・popcount** が適する表現（bitboard、集合演算、候補フラグ等）にできないか。CPU の命令対応も見る。
- [ ] [発展] [uops.info](https://uops.info/table.html) / [Agner Fog](https://www.agner.org/optimize/) を調べ、実際の CPU に近いマイクロアーキテクチャで命令特性を把握する。

> **直感**：独立命令を連続して発行できるなら「1命令のLatencyの総和」は実行時間の見積もりにならない。一方、同じ値を毎回更新する長い依存鎖ではLatencyが重要。CPUの実行能力に加え、キャッシュ・命令フェッチ・実行ポートも上限になり得る。

### 5.4 キャッシュ・メモリアクセス最適化

- [ ] [基本] **作業集合（working set）の大きさ**を見積もる。L1/L2/L3 に収まるかでランダムアクセスの実効コストが大きく変わる。
- [ ] [基本] **アクセス局所性**を上げる。連続アクセス（spatial locality）と、最近読んだデータの再利用（temporal locality）を意識する。
- [ ] [基本] 配列の**添字順序とループ順序**を一致させる。C++ の通常の二次元配列は行優先で、内側ループが右端の添字を進むと連続アクセスになる。
- [ ] [条件] ランダムアクセスが多いなら、データ圧縮・並び替え・候補のバッチ処理でアクセス先を近づける。
- [ ] [条件] 必要データだけ読む構造（SoA、hot/cold 分離）に変更する。大きな state 構造体の一部だけを大量に参照していないか。
- [ ] [条件] **キャッシュライン**（x86 では典型的に 64B）単位の転送と、境界跨ぎを意識する。隣接する値をまとめて触れるか。
- [ ] [発展] **セット連想度・競合ミス（conflict miss）**を疑う。特定のストライドや 2 の冪の行幅で同一キャッシュセットに集中していないか。
  - [ ] `A[1000][1000]` と `A[1024][1024]` のように、行幅変更だけで速度が大きく変わる場合がある。**単に 2 の冪に揃えることが正解とは限らない**。
  - [ ] パディング（`W + 1` 等）、データ転置、ループ順序変更、ブロック化のどれが効くか試す。
- [ ] [条件] 行列・二重ループ・巨大な盤面走査なら**タイル化／ブロッキング**してブロック内を再利用できないか。
- [ ] [発展] 再帰的な分割統治・**Cache-Oblivious** アルゴリズムで複数階層のキャッシュを利用できないか。再帰・インデックス計算のコストと比較する。
- [ ] [条件] 先読み（ハードウェアプリフェッチ）が効きやすい逐次アクセスか、予測不能なポインタ追跡かを区別する。
- [ ] [発展] メモリの読み込みが独立なら**Memory-Level Parallelism** を増やす。木の子ポインタを親から読んで初めて分かる構造は直列になりがち。
- [ ] [発展] キャッシュ容量だけでなく**TLBミス、ページサイズ、メモリ帯域**が律速でないか確認する。Huge Pages や手動プリフェッチは後回しでよい。
- [ ] [条件] 表を巨大化させる前計算が、メモリ帯域・キャッシュミスの増加でむしろ遅くなっていないか測る。

> **注意**：キャッシュ容量・セット数・ラインサイズは CPU ごとに異なる。スライドの実測例や「L1 に何KB」という数値は特定 CPU に関するもの。コードのレイアウト・実行環境で必ず再計測する。

### 5.5 コンパイラ最適化・アセンブリ確認

- [ ] [基本] **提出コンパイラ・C++ 規格・既定フラグ・CPU 命令セット**を確認する。ローカルと提出先を混同しない。
- [ ] [基本] `-O2` と `-O3` を比較する。**`-O3` が必ず速いわけではない**（コード肥大化や別のベクトル化判断）。
- [ ] [条件] `-Ofast` / `-ffast-math` は、NaN・Inf・符号付きゼロ・結合則・丸めなどの意味論が変わる。合法性・順位・受理判定への影響を検証する。
- [ ] [基本] `-ftree-vectorize` が必要かは**GCCの版と最適化レベル**で確認する。現行 GCC では `-O2` でも loop / SLP 自動ベクトル化が既定で有効で、pragma は魔法の高速化呪文ではない。
- [ ] [条件] C++ の `constexpr`、`consteval`、定数畳み込み、ループ不変式の巻き上げが利用できるか。動的除数をコンパイル時定数へできないか。
- [ ] [条件] `-march=native` は**そのCPU向け**に最適化する。提出先が異なる場合は対象 ISA を明示するか、標準的な命令セットを使う。
- [ ] [条件] GCC 固有の `#pragma GCC optimize` / `#pragma GCC target` や関数属性を試す場合、提出コンパイラ・関数ごとの適用範囲・命令対応を確認する。
- [ ] [条件] **Compiler Explorer**（[godbolt.org](https://godbolt.org/)）で本番に近いコンパイラ設定を使い、`idiv`、SIMD 命令、`call`、分岐、無駄なロードを観察する。
- [ ] [条件] `g++ -O3 -S -masm=intel` や `objdump -drwC -Mintel` でローカルの実際のバイナリを確認する。
- [ ] [条件] **自動ベクトル化の成否と理由**を確認する。GCC なら `-fopt-info-vec-optimized` / `-fopt-info-vec-missed` を使う。
- [ ] [条件] 小さな関数が本当にインライン化されたか、抽象化コストや不要な境界チェックが消えているかを見る。
- [ ] [条件] `__restrict__`（GCC拡張）やアラインメントのヒントで別名参照・ベクトル化が改善するか試す。ただし**事前条件を破ると未定義動作**になり得る。
- [ ] [発展] 生成されたアセンブリの依存関係・実行ポートを [llvm-mca](https://llvm.org/docs/CommandGuide/llvm-mca.html) などで静的解析する。ただし実測の代替ではない。
- [ ] [発展] PGO / LTO はビルド手順を制御できる場合に試す。競技ジャッジで自分がフラグ・学習済みプロファイルを渡せるとは限らない。
- [ ] [基本] **正しさ優先**：`-O3` でだけ壊れるならまず未定義動作・オーバーフロー・別名規則違反を疑う。`-fsanitize=address,undefined` などはローカル検証用。

> **環境メモ（2026-10確認）**：AtCoder の公式 [言語一覧（2026/06/16時点）](https://img.atcoder.jp/file/language-update/2025-10/language-list.html) の `C++23 (GCC 15.2.0)` は `-O2 -march=native` を含む。2026/06/15に当該言語の `-flto=auto` が削除された。**AHCの各問題・CodinGame の実行環境まで共通とは仮定しない**。提出時に再確認する。
>
> **Rust補足**：元メモの `f64::hypot` / `u64::abs_diff` は Rust の API 例。精度・オーバーフロー安全性・一般性を備えた API が専用実装より高コストになることがある、という観点を残す。

### 5.6 SIMD・自動ベクトル化

- [ ] [基本] **同じ演算を大量の要素に適用する箇所**を探す。例：一括評価、ビットセット操作、配列更新、密な行列処理。
- [ ] [基本] コンパイラがベクトル化しやすい**単純なループ・連続アクセス・固定された型**に書けるか。
- [ ] [条件] 各反復が独立か。ループ内の**逐次依存・関数呼び出し・間接参照・複雑な分岐**がベクトル化を妨げていないか。
- [ ] [条件] `if` をマスク演算などに変形するとベクトル化されるか。ただし不要な計算増・メモリアクセス増にも注意する。
- [ ] [条件] `uint8_t` / `uint16_t` / `int32_t` / `float` など型幅を選び、**1 SIMD 命令で扱える要素数**を増やせないか（精度、overflow、符号・変換コストを検証）。
- [ ] [条件] **AoS → SoA**、ストライド調整、アラインメントを試し、連続ロード／ストアで処理できるか。
- [ ] [条件] reduction（合計・最大値）は並列化可能な形か。`sum` の逐次依存を複数部分和に分ける手もある（浮動小数点では結果が変わり得る）。
- [ ] [条件] まず**自動ベクトル化 → 診断レポート → アセンブリ確認**を行い、効果が足りない場合のみ AVX2 / AVX-512 の intrinsics を検討する。
- [ ] [条件] SIMD には命令ごとの制約がある。一般的な整数除算のベクトル命令は乏しく、`gather`・変換・シャッフルが高コストなこともある。
- [ ] [条件] AVX2 / AVX-512 / `popcnt` 等を使う場合、**提出先のISA対応**を確認する。不一致は Illegal Instruction の原因になる。
- [ ] [条件] 512-bit が 256-bit の2倍速とは限らない。**クロック変動、メモリ帯域律速、マスク処理、短いループ**の影響を測る。
- [ ] [条件] ベクトル化したコードとスカラー版で、**数値一致・最終スコア・実測時間**を比較する。
- [ ] [発展] `std::simd` 系や [Google Highway](https://github.com/google/highway) などの可搬 SIMD ライブラリを検討する。ただしC++標準ライブラリへの収録状況とジャッジの実装対応を確認する。

### 5.7 高速なデータ構造・ライブラリ

- [ ] [条件] **セグメント木 → Fenwick Tree**：必要なのが一点加算・累積和などに限られるなら、定数倍とメモリで有利なことが多い。
- [ ] [条件] **`priority_queue` → Radix Heap**：非負整数の単調なキー（取り出す最小キーが減少しない）を扱うなら候補。
- [ ] [条件] **`std::set` → Fast Set / IndexSet / ビットセット**：扱う値域・必要操作に応じて選ぶ。
- [ ] [条件] **`std::sort` → SIMD sort**：大量の数値ソートが支配的なら [`x86-simd-sort`](https://github.com/numpy/x86-simd-sort) を比較する。
- [ ] [条件] **通常の FFT / 畳み込み → AVX2 最適化実装**：変換規模・係数型・精度・法・CPU 対応を確認して比較する。
- [ ] [条件] **全点対最短路 → 高速 Floyd–Warshall**：密なグラフで APSP が重い場合は [`quick_floyd_warshall`](https://github.com/windows-server-2003/quick_floyd_warshall) のような最適化実装を調べる。
- [ ] [条件] ヒープ値の更新が頻繁なら、インデックス付きヒープ／位置配列を併用する構造を使う（値変更 `O(log N)`・頂点取得 `O(1)` の設計など）。
- [ ] [条件] インデックスの小さい集合なら、bitset・配列上の木・Fenwick・sparse set 等をポインタ木より優先できないか。
- [ ] [基本] [Library Checker](https://judge.yosupo.jp/) や競プロライブラリの実装を読み、用途に合わせて比較・移植する。**ライセンスや提出制約**も確認する。

> **注意**：上記は「一律の上位互換」ではない。Fenwick Tree は一般のモノイド演算を扱うセグ木の代用にならず、Radix Heap も任意の優先度付きキューを置き換えられない。小さなデータでは特殊化のオーバーヘッドが勝ることもある。

### 5.8 プロファイリング・ベンチマーク・採否判定

- [ ] [基本] **何が律速か仮説 → 一箇所変更 → 同条件で実測 → 正しさ・スコア検証 → 採否**の順で進める。
- [ ] [基本] **Wall time、探索反復数、1反復あたりの時間、最終スコア**を記録する。Bot はターンごとの最大遅延も見る。
- [ ] [基本] `std::chrono::steady_clock` などの単調時計で経過時間を測る。時間計測自体がホットループを支配するなら間引く。
- [ ] [基本] マイクロベンチは**デッドコード削除（DCE）／定数畳み込み**を防ぎ、結果を観測可能にする。ただし `volatile` を多用して元コードと違うボトルネックを作らない。
- [ ] [基本] ウォームアップ、複数回実行、同じ入力／乱数シード、外乱の少ない環境を用意する。初回起動と定常状態を区別する。
- [ ] [基本] A/B の**実行順を交互にする**などして温度・周波数・OS スケジューリングによる偏りを減らす。単発の数%差を断定しない。
- [ ] [条件] Linuxで使えるなら `perf stat` で `cycles` / `instructions` / `branches` / `branch-misses` / `cache-misses` などを比較する。イベント定義や multiplexing に注意する。
- [ ] [条件] `perf record -g` / flamegraph などでホット関数を見つける（シンボル・デバッグ情報・フレームポインタの有無を確認）。
- [ ] [条件] IPC（instructions / cycles）・branch miss・キャッシュ miss・メモリ帯域の**どれが変わったか**を、速度改善の説明として確認する。IPC単独では性能を判定できない。
- [ ] [条件] WSL2・コンテナ・共有ジャッジでは、`perf` イベントが取れない／仮想化されることがある。取れない場合は時間と反復数、生成コード解析を優先する。
- [ ] [基本] **ローカルとジャッジの CPU / コンパイラ / 命令セット / 時間制限**を区別する。ローカルで勝った最適化がジャッジでも勝つとは限らない。
- [ ] [基本] 差分更新や低精度化をしたら**全再計算との一致、合法性、境界条件**を検証する。
- [ ] [基本] 高速化で探索量が増えたら、反復数だけでなく**同一時間での最終スコア**を評価する。必要なら探索パラメータを再チューニングする。
- [ ] [基本] 計測結果にコードコミット、フラグ、CPU、入力分布、シード、実行回数を残し、再現可能にする。

#### 最小の計測コマンド例（ローカル環境が対応する場合）

```bash
# ベクトル化の成否と不成立理由（GCC）
g++ -std=c++23 -O3 -march=native -fopt-info-vec-optimized -fopt-info-vec-missed main.cpp -o solver

# 現在のマシン向けのCPU特性と生成バイナリを確認
lscpu
objdump -drwC -Mintel ./solver | less

# Linux perf が利用できる場合（WSL2 では利用可否に差がある）
perf stat -r 5 -e cycles,instructions,branches,branch-misses,cache-misses ./solver < input.txt
```

| 症状 | まず疑うこと | 最初の試行 |
| --- | --- | --- |
| 反復数が少ない／重い関数が1つある | アルゴリズム・差分更新不足 | 計算回数を数え、重い評価を段階化 |
| `cycles` が多く、長い逐次依存がある | Latency／依存鎖 | 複数アキュムレータ、処理の独立化 |
| 分岐の多い乱択コードが遅い | Branch misprediction | 条件の並べ替え、分岐レス版との比較 |
| 配列を転置・拡大したら遅くなった | キャッシュ局所性／競合ミス | ループ順、パディング、タイル化 |
| 木・コンテナ操作が遅い | ポインタ追跡・個別確保 | 連続配列、pool / arena、専用構造 |
| `-O3` や SIMD にしても伸びない | ベクトル化不成立／メモリ律速 | 生成コードとmiss率、計算/byteを確認 |
| ローカルだけ速い・本番RE | ISA差異・未定義動作・環境差 | 提出環境の確認、UBSan/ASan、比較テスト |

## 6. CodinGame / 対戦 Bot 固有のチェック

> 以下は元のメモを対戦 Bot に適用するための**補足項目**。AHC にも共通するが、勝率・相手戦略・対戦分布の検証が重要。

### 6.1 プロトコル・合法性・再現性

- [ ] [基本] 入出力プロトコル・各フェーズ・合法手判定・特殊効果・勝敗条件を確認する。
- [ ] [基本] 標準出力を適切に**flush**する。標準エラーと標準出力を混同しない。
- [ ] [基本] 未知の状況・手札・盤面に対するフォールバックの合法手を用意する。
- [ ] [基本] 本番に近い時間・メモリ・コンパイラ・命令セットでテストする。
- [ ] [基本] シミュレータと公式ゲームの状態遷移が一致するか、ランダムな局面で差分テストする。
- [ ] [基本] 乱数シードと対戦ログを保存し、再現可能な失敗ケースを作る。

### 6.2 対戦戦略・探索

- [ ] [基本] 即時評価だけでなく、数手先の**相手の最善応答**を考慮する必要があるか。
- [ ] [条件] 完全情報・確定ゲームなら minimax／αβ／MCTS、運要素・隠れ情報があるならサンプリングや belief を組み合わせる。
- [ ] [条件] 対戦相手の戦略分布が偏っているかを調べ、汎用的な強さと特定相手への exploit を分ける。
- [ ] [条件] 相手方策の異なる複数 Bot で評価し、単一相手への過適合を避ける。
- [ ] [条件] 自己対戦だけでなく、旧版／ベースライン／異なる探索深さや方策を対戦相手に混ぜる。
- [ ] [条件] 局面に応じて探索計算量を可変にし、重要な意思決定へ時間を集中する。
- [ ] [基本] 目標指標は**勝率・レーティング等の対戦成績**。局面評価の改善だけで成功とみなさない。

## 7. 実験・検証・提出前チェック

### 7.1 実験設計

- [ ] [基本] 変更は原則一度にひとつずつ。どの変更が効いたか分かるようにする。
- [ ] [基本] **固定シード・同一ケース**で旧版と新版を比較する。乱数が影響するなら複数シードを使う。
- [ ] [基本] 平均だけでなく、中央値・下位分位・標準偏差・失敗率・ケース別の差を確認する。
- [ ] [基本] **探索回数／秒**と**最終スコア**を両方測る。速くなっただけで探索品質が落ちていないか。
- [ ] [条件] CPU高速化の検証では、探索の分布や乱数消費を揃えたマイクロベンチと、同一時間の本番スコア比較を**別々に行う**。
- [ ] [条件] 最適化フラグや SIMD 化を変えたら、生成コードの変化を確認し、ISA 互換性と浮動小数点評価順序を再検証する。
- [ ] [基本] 時間制限付近のケース、最大入力、境界入力、偏った分布を試す。
- [ ] [基本] 差分評価やキャッシュを導入したら、定期的な**全再計算との一致チェック**を追加する。
- [ ] [基本] 実験ログに変更内容・ビルドフラグ・シード・スコア・速度・制限時間を残す。
- [ ] [条件] 温度・近傍比率・ビーム幅などを系統的に探索し、パラメータへの過学習を確認する。
- [ ] [条件] ケース集合をチューニング用と検証用に分ける。
- [ ] [条件] 多スタート・Successive Halving などの探索割当ては、実際の最終性能に基づいて比較する。

### 7.2 メトリクスと失敗分類

| 見るもの | 意味・考えられる次の一手 |
| --- | --- |
| 最終スコアの平均・下位分位 | 全体性能と致命的失敗の有無 |
| ケース別改善差 | どの性質の問題で効くか、悪化するか |
| 1秒あたりの試行数 | 差分計算・前計算・メモリ改善の効果 |
| 有効近傍率・受理率 | 無意味な探索、温度や候補選択の偏り |
| 最良値の更新時刻 | 序盤に頭打ちなら大きい近傍・再加熱など |
| 初期解別／シード別分散 | 多峰性、未収束、初期解依存の可能性 |
| 最良状態への復帰頻度 | ロールバックが多すぎる／少なすぎる可能性 |
| Bot の相手別勝率 | 相手分布への過適合や苦手戦略の存在 |

### 7.3 提出直前

- [ ] [基本] 使っていない実験コード・デバッグ出力を消したか。
- [ ] [基本] 本番コンパイルで通り、提出環境の CPU 命令・言語バージョンに適合するか。
- [ ] [基本] 時間超過・メモリ超過・未定義動作・整数オーバーフロー・浮動小数点例外の問題はないか。
- [ ] [基本] AHC は出力の制約、CodinGame は各ターンのコマンドと flush を最終確認したか。
- [ ] [基本] **最良版の保存・復帰手段**を用意してあるか。直前の変更で成績を落とさないか。

## 8. うまくいかないときの診断フロー

1. **一部のケースだけ極端に弱い** → 失敗ケースの共通構造を見つける。状態制限、合法性、局所的なボトルネック、評価の欠落を優先調査。
2. **どのケースも少しずつ弱い** → 評価関数、将来性、近傍の候補品質、構築順序を確認。
3. **探索回数を増やしても伸びない** → 状態表現や近傍が狭い可能性。大きな近傍、多スタート、別表現を試す。
4. **探索回数に比例して伸びるが時間切れ** → まず差分計算・前計算・枝刈り。次に計測で、アロケーション／依存鎖／キャッシュミス／分岐／SIMD のどれが律速か分ける（第5章）。
5. **SA がすぐ停滞する** → 温度・受理率、近傍サイズ、再加熱、ロールバック、破壊＆再構築、スコア分布を調べる。
6. **ビーム幅を増やしても伸びない** → 重複・類似状態の排除、評価関数、遷移候補の多様性を確認。
7. **Bot が特定相手にだけ弱い** → 相手モデル、先読み、相性のある戦略、未観測局面を確認。
8. **ローカルでは改善、評価環境では悪化** → チューニング過学習、ケース分布、時間配分、実行環境差、乱数シード依存を疑う。

## 10. このリストに追記するときのテンプレート

```md
- [ ] [基本/条件/発展] **試すこと**：具体的な操作。
  - 成立条件：何が成り立つと効くか。
  - 期待する効果：探索回数増／候補品質増／局所解脱出／頑健性改善。
  - 検証：比較対象、指標、テストケース。
  - 結果：改善・悪化・不採用の理由。
```

> **重要な原則**：ヒューリスティックでは、「より速い実装」「より正確な評価」「より複雑な探索」がそれぞれ最終スコアに直結するとは限らない。**探索空間に良い解があるか → 良い解へ到達できるか → 同じ時間で何度試せるか → 本番の分布でも再現するか** の順に検証する。
