# 設計と制限

## 役割

- オーケストレーター（LLM、1体）：全記録を読み、行動 A・B・C を選び、案を書き、結果を読んで採否を決める。
- worker（LLM、独立）：自分の課題・問題・親だけを見て実装する。過去の得点や他の worker の結果は見ない。
- CLI（LLM なし）：作業場所の用意、worker の起動と後片付け、評価、記録、レポート、測定、調整。

## 評価の考え方

- 候補と現 best を、ラウンドごとの新しい seed で対にして比べる（効果 = seed ごとの差の平均、正ほど良い）。
- 多くの案の首位は、選んだのと同じ seed で測ると高めに出る（選抜の偏り）。実験では、終盤の採用の効果が前半500件 +0.088・後半500件 +0.002 だった例がある。そこで A は首位を未使用の seed で確認し、その値で採否を決める。
- 段階式の足切りは、明らかに悪い候補に1000件を使わないためのもの。上位 keep_top は必ず残す。差の小さい終盤では効かず、確認評価のぶん件数が約1割増える（docs/VALIDATION.md の V3）。
- 別ラウンドの平均点は seed が違うので比べない。採用の効果の足し上げは目安。
- 無効（TLE・RE・MLE・WA）は0点ではない。1件でも無効なら、その候補は無効。

## トークンを使わない工夫

- 案の数は1〜10（既定6。実験の試算では6案で10案の伸びの約84%）。共通の前提は common に1回だけ書く。
- worker の課題に、長いコマンドは1回の呼び出しで待つよう書く（codex の待つだけの呼び出しが R0017 で472回中314回あった）。
- 待つ・測る・調整するのは CLI（go --background、probe、tune、batchcheck）。オーケストレーターは待つあいだターンを終える。
- best を読み直さずに済むよう、worker の notes.md（変更点・構成・確かめられなかった点）を best/notes.md に写す。
- CLI の出力は短い表。

## 入れていないもの

非同期の worker、AB-MCTS、常駐プロセス、自動のモデル選択、自動提出、機械学習の学習管理、ダッシュボードのサーバー。

## 制限

- 作業場所の分離は、ファイルの置き場所と CLI の設定によるもので、悪意のあるプログラムへのセキュリティ境界ではない。codex は `--sandbox workspace-write`、claude は許可したコマンドだけで動かす。claude_deep は `python3 *` を許すので、任意の Python を動かせる。
- `human/private/` を読ませない仕組みは、claude には設定（.claude/settings.json）があるが、codex には指示（AGENTS.md）しかない。
- 利用上限・通信断の判定は、ログの文言に頼る。文言が変わると見落とす。
- 時計を遅く見せる `slowclock` は clock_gettime と gettimeofday にだけ効く（rdtsc を直接読むソルバーには効かない）。静的リンクのソルバーにも効かない。
- 手元の判定は AtCoder の判定と同じではない（コンパイラの版、マシン、メモリの測り方）。時間ぎりぎりの設定は提出して確かめる。
- レポートの「記録から拾った点」は決まった規則で数字を拾うだけで、意味は解釈しない。チェックリストとの照合は、文字の重なりでは正確でなかったので入れていない。
