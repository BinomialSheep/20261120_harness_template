# スコアと比較結果の読み方

まず、問題のスコアが大きいほど良いか小さいほど良いかを確認する。
この基盤の`mean_effect`は**正なら改善**になるよう向きをそろえている。最小化で候補80・基準100ならdifferenceは+20。
log_ratioなら最小化でlog(100/80)。0以下の値がある問題にlog_ratioを無条件適用しない。

`summary.json`の`raw_score_aggregate`は生スコアのケース平均/合計で、`mean_effect`は候補と基準の比較指標。
参加者全体の最高点や順位に依存する大会得点は、ローカル情報だけで求められないため既定null。

## レポートの読む順番

1. `status_counts`と`status_by_role`: WA/TLE/RE/基盤エラーがないか。
2. `case_effects`と`cases.csv`: どこで改善/悪化したか。タグから入力の性質を調べる。
3. `mean_effect`と`ci95`: 事前定義の母集団に対する差の推定。
4. `timing`: solverとjudgeの負荷を混同していないか。本番相当の余裕があるか。

失敗があれば全体判定invalid。成功例の診断は残るが、失敗例を除いた高得点を採用根拠にしない。
0点は合法なスコアかもしれず、失敗と同じ意味ではない。最小化のWAを0costにすると偽の最強候補になる。

同じ入力で10seedを試しても、独立入力が10個になったわけではない。反復はケース内にまとめ、入力blockで区間を作る。
少数ケース、多数候補からの選択、結果を見ながらの調整では偶然の勝者が出る。凍結候補を未使用ケースで確認する。
`positive_evidence`は自動採用でも、原因の確定でも、どの入力にも強い証明でもない。
