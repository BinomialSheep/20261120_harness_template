# 確認用ケースと、どれだけ測れば分かるか

開発時に何度も評価したケースは、そのケースに対してはよく分かる。しかし未使用の確認ではなくなる。v0.2では名前ではなく入力のSHA-256を使って露出を管理し、別名のケース集合へ入れてもauditを拒否する。

1. 少数ケースで接続テストを行う。
2. dev集合を凍結し、通常の改善・候補の選択に使う。
3. 予想効果が小さいなら、pilotのblock別スコアから `python3 -m harness precision ...` で大まかな必要実行回数を出す。
4. 予算内で判別できない実験を無限に反復しない。場合によっては原因診断か新しい解法系統を優先する。
5. 採用候補を決めた後、新しいケース集合でauditする。audit結果を見てさらに改変したら、その候補には次の新しいauditが必要。

v0.2では、同じaudit集合を複数候補へ順に使う運用を自動では許可しない。共同確認をする場合には事前登録された共同設計と露出台帳の仕組みを拡張する。単一の確認結果を何度も見て選んだ改善を「独立確認」とは呼ばない。
