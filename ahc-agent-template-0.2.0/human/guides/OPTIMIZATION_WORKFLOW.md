# 解法とパラメータを改善する

## コード変更と設定変更

同じartifactに異なるCLI引数/環境変数を与える候補は、suiteのvariantsとして区別する。
ソースhashが同じでも引数が違えば別の実験条件。`plan.json`は両方を保存する。

```json
{"variants":{"candidate":{"args":["--temperature","0.1","--seed","{solver_seed}"]},
             "baseline":{"args":["--temperature","0.2","--seed","{solver_seed}"]}}}
```

この例の引数はソルバー側の実装が必要。ハーネスが勝手に係数を書き換えるわけではない。
最終提出にCLI引数が存在しないなら、選んだ値をソースへ固定して再評価する。

## 固定反復と固定時間

SA近傍や探索順序の品質を見るには、固定反復数/ノード数が分かりやすい。
高速化の価値も含めた提出性能は、実際の時間制限下で確認する。時間依存探索は並列負荷で変わるため、最後は直列・排他で測る。
初期解、遷移、評価、近傍、終了制御のどこが効いたかは、可能な範囲で分けて考える。

## パラメータ探索の位置付け

Optuna等は必要になれば展開後に追加できるが、必須依存ではない。探索した候補数・消費したsolver_runsを隠さない。
係数調整で停滞したら、入力の構造利用や解法そのものの別系統も維持する。
多数候補の最高点は測定ノイズを拾いやすい。比較用集合と最終確認用集合を区別する。

評価ログを細かく取りたい場合は、solver stderrの形式を決めて別の診断器を追加する。ログ内の自己申告scoreは公式採点の代わりにしない。
